## V2.22 — 2026-10-11

**亮点：TAB 补全（首次交互运行自动安装）—— 主命令与 `watch` 子命令都能补，零配置**

对标 dmkit 的补全机制：**首次以交互方式运行 dmsqlq 时自动装好 TAB 补全**，
此后每个新终端自动同步；也可显式安装 / 撤销。

### 新增

- **TAB 补全（bash / zsh 通用，主命令 + watch 双形态）**：
  - `dmsqlq <TAB>` → 主命令全部选项（`-f --from -t --to -m --min-ms …`）+ `watch` 子命令 + 日志文件/目录
  - `dmsqlq watch <TAB>` → watch 专属选项（`-a --app -T --tail -i --interval --poll -g --gap -H --host -P --port …`）
  - 取值：`-k <TAB>` → `SEL INS UPD DEL DML DDL CAL ERR`；`-E <TAB>` → `CAL DDL SEL INS UPD DEL`；
    `-o/-r/-e/-O/-F/-d <TAB>` → 补文件名
  - zsh 用户免配置：脚本内 `autoload -U +X bashcompinit && bashcompinit` 自动启用
- **首次运行一次性自动安装**：以交互方式（stderr 为终端）首次运行任意命令时自动安装，
  写标记文件 `~/.dmsqlq/.completion_auto` 保证只触发一次。
- **显式命令（隐藏选项）**：
  - `dmsqlq --completion-install` 安装（幂等）
  - `dmsqlq --completion-install-dry-run` 只预览
  - `dmsqlq --completion-uninstall` 撤销（幂等）
  - `dmsqlq --completion-bash` 只打印补全脚本（供 `source <(...)` 用）

### 设计约束

- **绝不污染 stdout**：所有提示走 **stderr**，`dmsqlq . -o out.sql`、管道接别的工具等
  结构化输出不受影响。
- **仅交互终端触发**：stderr 非 TTY（管道 / 重定向 / CI / 远程执行）时静默跳过。
- **Windows 原生 cmd/PowerShell 跳过**（无 bash/zsh rc 体系）；Git Bash / MSYS / WSL /
  Linux / macOS 正常触发。
- **升级自动同步**：装过一次后，后续版本更新由 rc 区块的 mtime 比对在新终端自动刷新。

### 实现要点

- `src/dmsqlq.go`：新增补全模块（`dmCompMainFlags` / `dmCompWatchFlags` /
  `dmCompScript` / `dmCompBlock` / `dmManageBlock` / `dmCompInstall` / `dmCompUninstall` /
  `dmCompEnsureInstalled` / `dmCompHandleFlags` / `dmAutoInstallSupported`）；
  `main()` 在 `watch` 分流之后、正常解析之前处理隐藏补全选项并做首次运行触发。
  纯标准库，不引入任何第三方依赖，仍是单文件。
- 用法帮助新增「TAB 补全」一节。

## V2.21 — 2026-10-11

**亮点：`watch` 新增 `-H/--host`、`-P/--port` —— 可以从 WSL（或任何其他机器）连远端达梦实例了**

### 新增

- ⭐ **`-H, --host <地址>`** / **`-P, --port <端口>`**：指定要连接的达梦实例地址与端口。
  在此之前连接串是**硬编码** `SYSDBA/<口令>@127.0.0.1:<端口>`，只能在跑 dmsqlq 的同一台机器上连库。

  端口优先级：`-P` > 读到本机 `dm.ini` 的 `PORT_NUM` > `5236`。
  地址优先级：`-H` > 环境变量 `$DM_HOST` > `127.0.0.1`。

  典型用法（从 WSL 连 Windows 本机的达梦 —— WSL2 是独立网络命名空间 + NAT，
  `127.0.0.1` 在 WSL 里指向 WSL 自己，**必须**用 Windows 主机 IP）：

      dmsqlq watch /mnt/d/dmdbms/log -a manager.exe -H 172.20.240.1 -P 5236 -p <口令>

  连虚拟机测试环境同理，给那台虚拟机的 IP 即可：

      dmsqlq watch -H 192.168.16.135 -P 15236 -p <口令>      # 主备集群主库
      dmsqlq watch -H 192.168.16.133 -P 5236  -p <口令>      # 单机实验库

### 改进

- ⚠️ **`-Y` 加了远端安全护栏**：目标是**非本机地址**时，`-Y` **不再**自动切换同步刷盘
  （只照常执行只读体检）。理由三条：

  1. 同步刷盘对该库是实打实的性能开销，影响范围**远超本工具**；
  2. 还原依赖网络 —— 进程被强杀或网络中断时，库里会**永久停留在** `ASYNC_FLUSH=0`；
  3. 还原脚本落在**本机**临时目录，远端库出问题时现场未必找得到。

  要切刷盘，请到那台机器上用本机的 dmsqlq 执行（本工具只在 `127.0.0.1`/`localhost`/`::1` 时才改动配置）。

- 手工还原脚本里写出的连接地址改为**跟着 `-H` 走**（此前硬编码 `127.0.0.1`）。

### 修复

- 🩸 **修掉一个「加参数必踩」的老坑（V2.21 又踩一次）**：`watchRegroup` 的 `valNames`
  漏登记新参数时，**收值参数后面的值会被当成「日志目录」**——
  症状是「路径错误」，与「参数名写错」完全不同，更难认。
  本版给 `host/H/port/P` 补上登记，并在注释里写明这个症状特征。

### 实测

- **确定性测试 33/33**（与 V2.20 一致）+ 新增 `isLocalHost` 判据测试 **17/17**
- **批处理模式一行未动**：回归基线 `2,402,022 / 134,395 / 98.60%` 与 V2.20 完全一致
- 实测确认：`-H 127.0.0.1` 被正确当作参数值（不再被当位置参数）；`-H 172.20.240.1` 时连库失败会明确报错而非静默

## V2.20 — 2026-10-09

**亮点：`--sql-only` 改为「每条 SQL 之间空一行」—— 一批里没有分号的语句也能一眼数清**

### 改进

- ⭐ **`--sql-only` 下每条 SQL 之间空一行**：一批里有的语句**不带分号**（日志记的是客户端发来的原文，
  不是我们编的脚本），一行挨一行会「不知道是几条、看起来有点乱」。现在：

  - 同批内：每条之间**空一行**
  - 换批：之间**空两行**（多一行以示分组，不额外加任何要删的文字）
  - 配 `-g 0`：没有批次概念，统一一行一条

- **空行对执行无害**（这是敢默认加空行的依据）：《DM8_DIsql 使用手册》—— SQL 以 `;` 结束、
  语句块以 `/` 结束，而**脚本执行默认忽略 SQL 之间的空行**（`SET CTRL_INFO` 的 8 位才是「不忽略」）。
- ⚠️ 帮助里同时写清一件必须知道的事：**不带分号的语句粘进 disql 不会执行**。日志记的是客户端发来的原文，
  工具**不替它补分号** —— 末尾带 `--` 注释时补 `;` 会落进注释里（会静默少执行半条语句）。要跑请自行补。

### 实测

- 确定性测试 **33/33**（V2.19 的 31 项 + 3 项空行规则，其中 1 项由旧断言改写）
- **批处理模式一行未动**：回归基线 `2,402,022 / 134,395 / 98.60%` 与 V2.19 完全一致

## V2.19 — 2026-10-09

**亮点：`watch` 新增 `--sql-only` —— 只输出 SQL 原文，整段复制即用（不用再删元信息）**

### 新增

- ⭐ **`--sql-only`**：只打印 SQL 原文 —— **无元信息行、无批次头、无表头，且不缩进、不截断**。
  用途就是「把 SQL 复制出去执行」，例如看某个界面到底发了哪些 SQL：

      dmsqlq watch -a manager.exe --sql-only > click.sql

  批次之间仍空一行以示分组（配 `-g 0` 则连空行也没有）。
- **为什么不直接改默认**：元信息行里的「耗时」是判断**哪条慢**的唯一线索（V2.15 起一直保留），
  拿掉它就没法在「点一下界面发现慢」时定位到具体语句。所以做成开关，按场景选（详见设计说明 §9.22）。

### 实测

- 确定性测试 **31/31**（V2.18 的 27 项 + `--sql-only` 4 项：只出 SQL / 不截断 / 默认仍截断 / 空行规则）
- 真机实测：一条 210 字符的语句在默认模式被截断（带 `…`），`--sql-only` 下**完整保留**
- **批处理模式一行未动**：回归基线 `2,402,022 / 134,395 / 98.60%` 与 V2.18 完全一致

## V2.18 — 2026-10-09

**亮点：`watch` 输出改成「批次 + 紧凑表格」—— 同一批的 SQL 聚在一起，所有标题统一成「键: 值」**

### 新增 / 改进

- ⭐ **批次聚合**：默认把「**同一会话 + 与上一条的间隔 ≤ `-g`（默认 1000ms）**」的记录聚成一批 ——
  点一次界面带出的十几条 SQL 会**放在一起**，不再散落在流水里。每批给出：
  批次标题（`── 批次 N · 时刻 ──`）、本批共用的键值行（会话 / 客户端 / 用户 / 线程号 / IP）、
  行内列表头，以及收尾行「**共 N 条 · 累计 X · 跨度 Y**」（下批开始 / 静默超时 / 退出时打印）。
- ⭐ **所有标题统一成「键: 值」**：启动横幅（跟随 / 路径 / 过滤 / 轮询 / 批次 / 列说明）与汇总
  （观察时长 / 输出条数 / 批次数量 / 按类型）都改成 `键: 值`，与批次头一致。
- 新增 **`-g, --gap <毫秒>`**：批次的最大间隔；**`-g 0` = 不聚合**，退回扁平表。
- **重定向 / 接管道时自动走「扁平模式」**（与 V2.17 完全相同的形态：10 列元信息行 + SQL 独占行），
  保证数据流规整、方便 `grep`/`awk`；想让它带批次就显式给 `-g`。
- 数值列的列标题一并改为右对齐，跟数据对齐（`事务号` 不再离数字老远）。

### 修复

- 🩸 **`-g` 漏登记进 `watchRegroup` 的「收值选项」名单** → `-g 1000 -T 3000` 报
  `参数有误：invalid value "-T" for flag -g` —— 重排参数时把 `-g` 当成了布尔选项，于是它把
  下一个选项名当成自己的值吞掉。已修，并把这条判据写进技能（每加一个收值选项都要补 `valNames`）。

### 实测

- 确定性测试 **27/27**（V2.17 的 17 项 + 批次模式 10 项：批次标题、同会话聚 3 条 / 累计 317 ms / 跨度 800 ms、
  超时与换会话各另起一批、每批都有收尾行、批次头是键值形式、行内只留变化列、批内 SQL 缩进 4 空格、
  批内不空行且批间空行、横幅与汇总键值形式、`-g 0` 退回扁平）。
- 追加→显示延迟 **0.11 秒**（轮询 100ms）；真机回放：DM 管理工具每 5 分钟的轮询各自成一批。
- **批处理模式一行未动**：回归基线 `2,402,022 / 134,395 / 98.60%` 与 V2.17 完全一致。

## V2.17 — 2026-10-09

**亮点：`watch` 的「管道友好」改造 —— 数据走 stdout、诊断走 stderr；下游断管即退出**

### 新增 / 改进

- ⭐ **数据与诊断分流**：**记录写在 `stdout`**；横幅 / 表头 / 切换提示 / 汇总在**「stdout 被重定向或接管道」时改走 `stderr`**。
  → `dmsqlq watch -a manager.exe > run.log` 得到的文件里**只有记录**；`| grep x` 也不会被横幅占掉配额。
  stdout 是终端时两者仍都走 stdout，**观感与之前完全一致**。
  判据用 `isTerminal`：Windows 控制台是字符设备，管道是 `ModeNamedPipe`，普通文件是普通文件。
- ⭐ **下游关闭管道时退出**：每次写记录都查错，写入失败即收尾（打印汇总后退出）。
  改版前 `dmsqlq watch … | head -3` 这类用法会在 Windows 上留下一个**永远轮询的孤儿进程**
  —— Windows 没有 SIGPIPE，write 只返回错误、进程不会自己死（Linux/macOS 会被 SIGPIPE 直接结束）。
  ⚠️ 边界：只**在写出时**才能发现 —— 下游关闭后若长时间没有新记录，工具会继续跟随（按 Ctrl-C 即可）。
- 帮助新增 **「管道」** 一节，含 `grep --line-buffered` 这个必踩的坑（grep 的输出不是终端时会块缓冲）。

### 实测

- 确定性测试 **17/17**（新增两项：stdout 只有记录 / 横幅在 stderr）。
- 定向验证：`> 文件` 时 stdout 只有记录、stderr 是横幅与表头；
  `| grep --line-buffered "v$open_stmt"` 只命中 SQL 行、**无横幅噪声**；追加→显示延迟 0.09 s。
- **批处理模式一行未动**：回归基线 `2,402,022 / 134,395 / 98.60%` 与 V2.16 一致。

## V2.16 — 2026-10-09

**亮点：`watch` 输出 —— 同一秒内的多条记录之间空一行**

### 改进

- ⭐ **同一秒内执行的多条记录之间空一行**：一次界面点击常带出十几条 SQL，它们的时间戳**完全相同**
  （如 `12:23:37.833 / .849 / .896`），原来挨着排会**糊成一片**、看不出一条记录到哪儿结束。
  现在同一秒内的记录彼此空一行。
- **不同秒的记录之间不加空行** —— 时间戳本身已经把边界分得很开，没必要再撑高输出。
- 判定口径：拿**上一条已输出记录**的秒（`HH:MM:SS`）来比，相同则先打一个空行；**回放与实时走同一条路径**，行为一致。

### 实测

- 确定性测试 **15/15**（新增两项：同一秒空一行 / 不同秒不空行）；追加→显示延迟 0.09 s。
- 真机回放：`12:23:37.833 → .849 → .896` 三条之间各有空行；`12:22:13.311` 与 `12:23:37.833` 之间无空行。
- **批处理模式一行未动**：回归基线 `2,402,022 / 134,395 / 98.60%` 与 V2.15 一致。

## V2.15 — 2026-10-09

**亮点：`watch` 输出改版 —— SQL 单独成行可直接复制，并补齐线程号 / 用户 / 事务号 / 应用名 / 会话 / IP**

### 新增

- ⭐ **SQL 独占一行**：一条记录打印两行 —— 第 1 行是元信息（对齐成表），第 2 行是 SQL 原文（缩进 2 空格）。
  改版前 SQL 与时间、耗时挤在同一行，**复制时会把时间与耗时一起带走**；现在只选第 2 行就是干净的 SQL。
- **新增 6 列**：`线程号`(thrd) · `用户`(user) · `事务号`(trxid) · `应用名`(appname) · `会话`(sess) · `IP`；
  加上 `时间` / `类型` / `耗时` / `行数`，共 10 列。
- **启动时打印「列说明」**，逐列解释含义与口径（其中 `耗时 = EXECTIME`，★**含等锁时间**）。
- **宽度不够自动丢列**（会话 → IP → 线程号 → 用户 → 事务号），并在横幅里写明省略了哪些、怎么显示出来。

### 实测结论：句柄号为什么没进这张表

- ✅ **`会话` 可以关联回库**：日志头部的 `sess:` 与 `V$OPEN_STMT.SESS_ADDR` **取值完全一致**
  （实测 `sess:000000000FBD0D20` ↔ `SESS_ADDR = 0x000000000FBD0D20`），且该行的 `SQL_STR`
  正是日志里那条 SQL。→ 拿着日志里的「会话」地址，就能在库上把这条语句查出来
  （再由 `SESSION#` 连 `V$SESSIONS` 取 `SQL_TEXT / USER_NAME / TRX_ID / CLNT_IP / APPNAME / STATE`）。
  用法见 `使用说明.md` §11.7。
- ❌ **`句柄号` 查不到**：`V$OPEN_STMT` 只给每个会话的 `STMT_ID`（**序号，不是地址**），
  唯一的语句句柄地址列 `STMT_DBG` **只在调试会话时非空**；`V$STMTS` 也只有 `STMT_ID`。
  → 本次**不展示**句柄号。
- ❌ **执行节点 `EP[n]`**：单机恒为 0，没有信息量，不展示。

### 改进

- 「回放最近 N 行」的横幅移到**表头之前**（原来夹在表头与记录之间，看着像打错了位置）。
- 元信息行去掉行尾空格。

### 实测

- 确定性测试 **13/13 通过**（新增 3 项：SQL 独占一行 / 元信息行含新列 / 元信息行不含 SQL 文本）；
  追加→显示延迟 **0.07 秒**（轮询 100ms）。
- 真机：本机 `disql` 执行 SQL 被实时捕获，新增各列取值正确。
- **批处理模式一行未动**：回归基线 `2,402,022 / 134,395 / 98.60%` 与 V2.14 一致。

## V2.14 — 2026-10-09

**亮点：`dmsqlq watch` 不用再给日志路径（自动定位）；给口令还能顺手做采集体检、并临时切成同步刷盘（退出自动还原）**

### 新增

- **自动定位日志目录（零参数）**：`dmsqlq watch -a manager.exe` 直接可用。
  顺序：`-d`/位置参数 → `$DMSQLQ_LOG_DIR` → 上次用过的目录（记住）→ 扫 DM 安装目录
  （各盘的 `\dmdbms`/`\dm8`/`\dameng`/`\dmdata`；Linux 的 `/opt`、`/data`、`/usr/local`、
  `/home/<用户>` 下同名目录），读其中 `sqllog.ini` 的 `FILE_PATH`，也直接找含 `dmsql_*.log` 的目录。
  多个候选按「最近写过日志」挑；横幅会说明路径来源，并提示还发现了哪些、怎么换。
- 新增 `-d/--dir`、`--show-paths`（只列候选与最近活动时间）、`--forget`（清掉记住的路径）。
- **`-p/--pass`（或 `$DM_PASS`）+ `-Y/--sync-log`**：

  ```bat
  set DM_PASS=<你的SYSDBA口令>

### 🩸 一个必须记下的坑：`SP_SET_SQLLOG_INI` 的模式名写法不能照抄 sqllog.ini

`V$DM_SQLLOG_CONFIG` 报出的模式名可能和 `sqllog.ini` 里的段名**不一样**：
本机报 `<DEFAULT>`（文件里写的是 `[SLOG_ALL]`）。此时

### 起因（一轮构造实验）

现场一直有一句没被证实的判断：「锁等待的根持有方只有 23% 能拿到 SQL，其余只有

- `kill -9` 中止的持有方**照样有 SQL**（形态是 `[ERR(-6007)]: <完整SQL> EXECTIME: N(ms)`）

### 新增

- **`[ORA]` 兜底溯源**：掩码 27 的 `[ORA]` 行**不受 `MIN_EXEC_TIME` 限制**（实测 0.4ms 的 UPDATE 也有），
  且带 `sess` + `stmt` 句柄，与持有方事务的 `PARAMS`/`DLCK` 行**完全一致**
  → 采集期建 `(sess,thrd,stmt) → SQL` 与「事务号 → 语句键」两张表，报告期对「没有执行行 SQL」的
  持有方自动兜底填充，并**显式标注来源**（HTML 卡片、终端、MD、Excel 四处）
- **实测效果**：持有方 SQL 可得性 **0/1 → 1/1**（133 `lab_ora27.log`）

## V2.11 — 2026-10-08

**亮点：报告新增「锁等待排查方向」—— 把「谁在持锁」变成「你该往哪儿查」**

### 起因（现场提问）

报告把根事务的**结局**（提交 / 回滚）逐张卡片列出来了，用户看完问：

> 「持有方（链首）结局全是回滚，所以问题排查方向是什么？……

这是一个很准的提问：**报告给了数据，却没给路径**。这些信息分散在几十张卡片里，
读者得自己横着看才能拼出结论 —— 那本该是报告替他做的事。

### 新增：锁等待「排查方向」一节

按**日志能证实的顺序**逐步缩小范围，每步都写清三件事：
**① 日志能证实的事实（实测）→ ② 怎么读（推断，并写明日志不能证明什么）→ ③ 往哪查**。

本次实测日志自动得出的 5 步：

| # | 标题 | 自动算出的事实 |
|---:|---|---|
| 1 | 先看根事务的结局分布 | 根事务 44 个：**回滚 31 / 提交 10 / 未见结束 3** |
| 2 | **再看回滚时刻是不是成簇**（最有用） | **15 个根事务在 2.51s 内集中回滚**（09:06:56~09:06:59，占全部回滚的 48%） |
| 3 | 确认是不是多个会话在做同一件事 | 同一条语句出现 **35 次**；根事务分布在 44 个不同事务上 |
| 4 | 看根事务为什么能持锁这么久 | 最长 26.88s；120 次等待里 **92 次**的持有方拿不到语句文本 |
| 5 | 下次复现时在库上抓现场 | 给出 `V$TRXWAIT` / `V$SESSIONS` 的可复制 SQL |

**第 2 步是本版的核心价值**：把「回滚」这件事从"结果"推进到"形态"——
**多个根事务在同一秒内集中回滚**，形态上更像「应用侧一次性把这一批全部回滚」，
而不是各事务各自失败。**但报告会明说这只是形态推断，日志证明不了原因，要去应用日志确认**——
延续「不替读者下没有依据的结论」的一贯原则（§9.7）。

> ⚠️ 同时更正一个容易想当然的说法：**并不是「结局全是回滚」**——
> 本次实测 44 个根事务里 **31 个回滚、10 个提交、3 个未见结束**。
> 只有**前几名的大型链**的根事务都是回滚。报告把这三种结局分别列出，不合并成一句"全是"。

## V2.10 — 2026-10-08

**亮点：「优先优化推荐」不再把**等锁受害者**当成优化对象 —— 现场直接质疑过这一点**

### 问题（用户原话）

报告把这条排在第 1 位「优先」，并建议「抓最快与最慢各跑一次 EXPLAIN 对比」：

```
1 [优先] 影响占比 28.7%  28 次 · 最快 500ms / 平均 18.04s / 最大 25.99s · 累计 8.4min
  INSERT INTO T_IM_INV_PER_BAL_KL (FKEYCOL) VALUES (2585533804449946624)
```

用户一看就反问：**「怎么会是一条 INSERT，这能有什么优化空间？」** —— 问得对。

### 真相：那不是慢 SQL，是等锁

用日志自身对账即可定案：

| 项 | 值 |
|---|---|
| `T_IM_INV_PER_BAL_KL` 的 INSERT 累计耗时 | **505.0 s** |
| 该表（ID 76196）上的锁等待累计 | **505.0 s** |
| 占比 | **100.0%** |
| 逐事务核对 | 等锁耗时与语句耗时**差值 0.00**（25.84 vs 25.84 / 25.50 vs 25.50 …） |

那 18 秒平均耗时**几乎全是等 X 锁**；语句本身是主键单行插入，快得不能再快。
**去 EXPLAIN 它什么也看不出来** —— 误报比不报更坏：会让人去改没问题的写法。

而且这不是个例：本次报告前 3 名**全是**这类（三张热表的单行 INSERT），
合计 **22.8 分钟、占全部语句耗时的 77.6%**。

### 新增

- **「等锁」判定**：一条语句模板如果满足
  「**同表锁等待累计 ÷ 该模板累计耗时 ≥ 60%**」，就判定为**等锁受害者**：
  - 优先级标签由「优先」改为 **`[等锁]`**（HTML 用独立色系，一眼区分"这不是最该改的 SQL"）
  - 问题信号 → `等锁，不是语句本身慢`
  - 建议动作 → 明说「**改这条 SQL 没有收益，EXPLAIN 也看不出问题**；要动的是持有方 ——
    见「锁等待」一节的阻塞链，处理那个长时间持锁的根事务」
  - **排序（影响占比）保持不动**：这份耗时是真实发生的，账要照记，
    只是把动作指向真正该动的地方
- **表名 → 锁等待累计**索引（`statsView.LockSumByName`）：
  用**全量** `st.LockByTable` 构建（不受 `-p` 截断影响），名字优先 `--obj-map`、其次用 V2.8 的投票推断

### 修复

- 🩸 **Excel 交付件的「优先级」列与 HTML/MD/终端不一致**：
  Excel 那份清单**自己按占比重算**优先级，于是同一批数据里
  Excel 显示「优先」、HTML 显示「等锁」—— **两个视图打架**。
  现在 Excel 走同一个 `lockVictim` 判定，四处口径统一。
- 🩸 **`recommend()` 建得太早**：它依赖锁统计，而原先在**结构体初始化时**就算 ——
  那时 `LockSumByName` 还是空 map，**判定静默失效**（改了代码、编译通过、
  跑起来那条 INSERT 仍被当成优化对象，就是踩了这个）。
  已移到锁等待段之后统一计算。
  → 与「交付件视图必须建在 `writeFullSQL` 之前」是同一类坑：**视图要建在数据就绪之后**。

### 实测

- 修完后同一份日志：前 3 名全部标为 `[等锁]`（各 100%），
  第 4/5 名（`SELECT count(1)…` 469 次 / 145ms、341 次 / 155ms）才是真正的 SQL 调优候选
- 回归基线（`D:/dmsql_log` 15 文件 / 2.0 GB）：**2,402,022 / 134,395 / 98.60%** —— 与 V2.9 一致
- 扫描耗时交错对照：V2.9 2.355~2.384s vs V2.10 2.235~2.297s —— 无退化（本次机器整体偏慢，
  但两版同机对照新版略快，在噪声内）

## V2.9 — 2026-10-08

**亮点：识别采集侧的 `MIN_EXEC_TIME`（最小执行时间过滤）；修掉一处自相矛盾的掩码结论**

本版源于一次真实的误判：现场日志里 **UPDATE 一条都没有**，而同期实例日志显示
**重做日志 3 分钟涨 635 MB、归档文件 16 分钟长 2 GB** —— 写量远大于日志里记到的写语句。
第一反应是「UPDATE 采集位没开」，**结论是错的**。

### 新增

- **「最小 EXECTIME」体检项**：自动检测日志里最快那条语句的耗时，
  若**恰好卡在整数阈值上**（1/5/10/20/50/100/200/500/1000… ms），
  就提示**极可能采集侧设了 `MIN_EXEC_TIME`**，并明说
  「**低于该值的语句不写日志，且与语句类型无关**；此时『日志里没有某类语句』
  （如 UPDATE / DELETE）**不代表掩码漏开**」。
  - 实现上**不新增热路径字段** —— 由报告期已有的耗时直方图最低非空桶反推（桶精度约 ±15%），
    采集开销为零。实测那份日志算出 **100ms**，与真实最小值 100.00ms 一致。
  - 实测抽检该库：`MIN_EXEC_TIME = 100` 生效的铁证是
    **1729 条执行行里 0 条低于 100ms**、直方图在 100ms 处硬截断。

### 修复

- 🩸 **修掉一处会自相矛盾的掩码结论**：用 `-f/-t` 过滤出时间窗口后，
  「判读提示」会写「**日志里没有任何锁/事务事件行**：先确认 `SQL_TRACE_MASK` 是否含 29」，
  而**同一份报告的锁等待小节**刚说过「位号 29 已开、这个 0 可信」——
  两句话打架。根因是把「**日志的属性**（掩码有没有开）」和
  「**本次范围内的行数**（窗口内当然没有事务事件）」混用了。
  现在该分支改为按 `Mask29On`（整份日志判定）区分，窗口过滤下也只会说
  「位号 29 已开（日志里有 N 条事务事件），本次范围内一条锁等待都没有 —— 这个 0 可信」。

### 为什么要加这条（一次真实的归因错误）

现场配置是 `SQL_TRACE_MASK = 2:3:25:28:29` ——
**位号 2 = DML = 等同同时设置 4~10，本来就包含 UPDATE(4) 与 DELETE(5)**，掩码没问题。
真正的过滤器是同一份配置里的 **`MIN_EXEC_TIME = 100`**（毫秒）：

- 它是**全类型通杀**的：不分 SEL/INS/UPD/DEL，只要单条 <100ms 就不写日志
- 所以 **DELETE 同样会「漏」** —— 实测该库 15 分钟只记到 4 条 DELETE，
  耗时 125 / 107 / 167 / 234 ms，**全部 ≥100ms**，与配置完全自洽
- 「重做涨 635MB 却只有 1 行写」也因此解释清楚：不是有隐形 UPDATE，
  而是**大量很快的写操作被逐条滤掉了**（ERP 每秒几百条小事务，单条几十毫秒很正常）

> **教训（已写进技能）**：**「日志里没有」不要直接归因到掩码位** ——
> 先看 `MIN_EXEC_TIME`；而且**看配置文件比推理快**：
> 线上 `sqllog.ini` 明摆着 `2:3` 已含 UPDATE，读一眼就能避免这个误判。

### 回归

- 基线（`D:/dmsql_log` 15 文件 / 2.0 GB）：**2,402,022 / 134,395 / 98.60%** —— 与 V2.8 一致
- 扫描耗时与 V2.8 交错对照在噪声内（2.055~2.096s vs 2.069~2.121s）——
  新指标纯报告期计算，热路径零新增

## V2.8 — 2026-10-08

**亮点：锁等待给出「双方的 SQL」+ 阻塞链；对象 ID 自动反推表名（免手工查字典）**

本版来自现场反馈：「锁等待的分析很有价值，但输出信息不直观，希望能看到锁持有者事务的所有 SQL」。

### 新增

- **锁等待双方的 SQL**（HTML 卡片 / Markdown / 终端 / Excel 四处同步）。
  一张卡片 = 一次锁等待：左边是**等待方当时在跑的那条 SQL**（参数已还原），
  右边是**持有方（链首事务）在日志里的语句 + 结局**（提交 / 回滚 + 时间），
  并注明它后面还排了几个事务。
  - 关联方式：掩码 29 的锁行只给 `trxid`，语句文本在另一类行上；本版按 trxid
    把语句挂到事务上再反查。
- **阻塞链**：日志的持有方列表是**累计排队**的 ——
  `wait for 7 trxs, trx[A, B, C, …]` 里 **A 才是真正持锁的**，B、C… 全堵在 A 后面。
  本版按「表 + 链首」聚成链，直接回答「哪个事务、把多少人堵了多久」。
  实测本批日志最长一条链排了 **18 个事务**。
- **对象 ID → 表名自动推断**：DM 的 SQL 日志只记 `table id` 不记表名，以往要靠
  `--obj-map` 手工查数据字典。本版用**等待方 SQL 里出现的表名**给同 ID 投票
  （X 锁下写目标表权重更高），报告里以「推断」标注；`--obj-map` 仍然优先。
  实测本批 4 张热表 **100% 推对**：76197→`T_IM_CAL_PER_BAL_KL`、
  76196→`T_IM_INV_PER_BAL_KL`、76193→`T_IM_INV_REALBALANCE_KL`、83099→`T_CAL_BAL_KL`。
- **锁等待明细不再受 `-p` 显示上限约束**（保留上限提到 5000 条）——
  原先只留 20 条，等于报告只覆盖了 1/6 的锁等待。

### 改进

- **「没采集到」与「没执行」严格区分**：持有方事务常常只留下
  `TRX: START` / `PARAMS` / `alloc pseg`，没有语句文本行。报告会**明说**原因，
  而不是留空让人误判。
- 🩸 **追查后的结论（2026-10-08 追加，修正了本版初稿的表述）**：初稿写的是
  「语句文本没进日志（掩码 2~17 没开全）」，**这个解释是错的**。实测证据：
  同一个参数值 `'BxNUIbI5B1gt4nHwSC1D6qbpIrmu6qzygJuCTSaeueM='`、同一条
  `INSERT INTO T_IM_CAL_PER_BAL_KL (FKEYCOL) VALUES (?)`，在**等待方**那边有**27 条**
  完整执行行（`EXECTIME` 齐全），而**根持有方**一条都没有 —— 采集位若没开，
  等待方也不该有。真正规律是：
  - **有 SQL 的**都**当过等待方**：等锁 → 拿到锁 → 语句跑完 → 写完成行 → 事务回滚
  - **没 SQL 的**都是**只持锁、从未等待**的根持有者：一直持锁 → 被中止 → 只有 `ROLLBACK`
  **回滚与采集无关**（107 个回滚的持有方里 28 个有 SQL；全库 564 个事务是「有语句+回滚」，
  本次对比的 5 个事务更是全部回滚，差别只在「是不是根持有者」）。
  报告措辞已随之改为「语句**只见开始、没有完成行**（通常是没跑完就被中止）」，
  并说明**补采日志没用**，要在库上抓 `V$SESSIONS` / `V$SQL` 快照或开 SQL 审计。
- 可得性如实写在标题栏：实测本批 **等待方 SQL 106/120（88%）、持有方 28/120（23%）**。

### 实测（KD1 2026-10-08 单文件 1.0 GB / 500 万行）

- 锁等待 **120 次**（80 次持有方列表完整 + 40 次被日志截断成 `...more`），
  涉及 4 张表、44 条阻塞链，最长等待 **26.88s**（根事务持锁 26s 后**回滚**）。
- 回归基线（`D:/dmsql_log` 15 文件 / 2.0 GB）：**2,402,022 / 134,395 / 98.60%** —— 与 V2.7 完全一致。
- 扫描耗时与 V2.7 相当（交错对照 ±3% 内）。

### 🩸 两个实现上的坑（都已在源码注释里写明）

- **溯源缓冲不能挂在共享的 `Stats` 上**：初版把「事务→语句」存在 `Stats` 的切片里，
  6 个 goroutine 抢着改切片头造成缓存行争用，2.0 GB 扫描从 2.29s 退化到 2.71s（+18%）。
  改成挂在**每个文件独占的 `parser`** 上（单线程、零锁），文件结束 `defer` 合并，回到 ±3%。
- **不要按 PARAMS 行记账**：PARAMS 行现网百万级，两种记账方式（string 键 / 零分配 uint64 键）
  都把扫描拖到 3.8~4.3s —— 这点信息不值得毁掉速度卖点，改用「事务有没有语句行」表达同一件事。
- **不要用语句句柄 `stmt:0x…` 关联**：它是会话命令缓冲的地址、会被复用
  （实测同一句柄 6 分钟后挂到另一条完全不同的语句上），拿它当键必然串错。

### ⚠️ 已知限制（与本次改动无关，但在锁场景下会被放大）

- **参数还原可能配错单参数语句**：同一句柄多次执行时，工具靠「参数个数相等」防错位，
  个数为 1 时无法区分，可能拿到该句柄另一次执行的参数。
  实测 `INSERT INTO T_IM_CAL_PER_BAL_KL (FKEYCOL) VALUES (?)` 被还原成 `(0)`，
  而该次执行 PARAMS 行里的值其实是加密串 `'BxNUIbI5…='`；
  用 `-x <事务号>` 抽取也是同样结果，**属于既有行为**，非本版引入。
  影响面：所有视图的「参数已还原」标注。规避：单参数语句以日志原文为准，
  或按 `EXEC_ID` 到库里核对。

## V2.6 — 2026-10-02

**亮点：修正「问题信号」误报；模板加「最快」列；QPS 被低估时显式告警**

本版来自现场使用反馈（用户指出报告里的两处判读问题），都是**数据正确但结论误导**的类型。

### 新增

- **「最耗时语句模板」增加「最快」列**（HTML / Markdown / 终端 / Excel 四处同步）。
  为什么重要：**只给平均和最大，看不出优化方向**。
  - 最快 ≈ 平均 ≈ 最大 → **稳定慢**，是结构性问题（缺索引 / 写法），改了就有效果；
  - 最快 ≪ 平均 → **时快时慢**，是计划突变、数据倾斜或偶发锁等待 ——
    这时先去查"为什么不稳定"，而不是急着加索引。
- **新信号「快慢差异极大」**：最快与平均差一个数量级以上时给出，并直接说明
  "**不是单纯缺索引**"，建议分别抓最快与最慢那次的语句各跑一次 EXPLAIN 对比。
  这条排在其它耗时形态之前 —— 它决定的是优化方向，比"平均慢"更有信息量。
- **新信号「运行时动态 DDL」**：识别 `DECLARE ... EXECUTE IMMEDIATE 'CREATE INDEX ...'`
  这类"先查字典判断存在性、再动态建对象"的脚本。
  实测现网有个模板这样跑了 **17,613 次**（每次都要跑一遍字典查询 + 建对象判断），
  高并发下会争抢字典锁、拖慢所有会话。
- **新信号「超长 IN 列表」**（≥100 个字面量）：实测有个模板拼了 **999 个值**、
  单条 SQL 文本 **49 KB** —— 恰好卡在 DM 的 IN 上限 1000 附近。
  IN 值过多会让优化器逐个估算代价、生成巨大执行计划，还可能因选择性判断失真而放弃索引。
- **新信号「单次取数过大」**（≥5000 行）：实测有模板每次取 **11,000 行**。
- **QPS 被低估时显式告警**（HTML 红色告警条 / Markdown 引用块 / 终端提示）——
  见下方「修复」的说明。

### 修复

- 🩸 **「SELECT * 取全字段」是误报**（现场反馈）。原判据只做
  `strings.Contains(up, "SELECT *")`，于是把现网 TOP 模板全判成了取全字段 ——
  而它们实际是 DM 的**双层分页惯用法**：
  ```
  SELECT * FROM (SELECT TOP 0, 11000 <明确列清单> FROM ... ORDER BY ...) WHERE ROWNUM <= 11000
  ```
  **星号在包装层上，内层列写得清清楚楚**（有个模板内层只取 3 列），根本不存在"多取列"。
  修法：先剥外层包装、对内层诊断；`SELECT *` 只在**直接查基表**（FROM 后不是括号）时才报。
  在 20 个真实模板上验证：**零误报**，且换来了上面几条更有价值的信号。
- 🩸 **QPS 与 TPS 不可横向比较，报告以前没说**。现场发现报告显示
  平均 QPS **1.63 条/秒**、平均 TPS **499.57 事务/秒** ——
  同一个库不可能"每秒提交 500 个事务却只执行 1.6 条 SQL"。查下去是**采集密度**问题：
  - 单文件实测（1.08 GB）：SQL 执行行 `[CAL]315 + [INS]106 + [SEL]52` = **473 条**，
    而 `PARAMS` 行 **4,074,062 条**、`TRX: COMMIT` **38,670 条**；
  - 单个预编译句柄 `stmt:0x7feeb4c35638` 就对应 **53,891 条 PARAMS 行**，却只有极少执行行。
  - 即：**COMMIT 行是 SQL 执行行的 80 多倍**。所以 QPS 只是"日志里记到的语句数"，
    **不是业务真实吞吐**，与 TPS 口径不同、覆盖度差两个数量级。
  修法：当事务结束事件数 > SQL 事件数 × 20 时，报告显式告警并给出核对方法
  （`SELECT PARA_NAME,PARA_VALUE FROM V$DM_SQLLOG_CONFIG`）。
  这与 V2.4 的「锁等待 0 次 vs 没采集」是同一类问题 ——
  **报告不能把一个"因为没采到所以偏小"的数字当作业务事实呈现**。

### 实测

- 回归基线逐项一致（15 文件 / 2.0 GB）：2,402,022 / 134,395 / **98.60%**，2.011 s
- 中垦乳业 9:00–18:00 窗口重跑，TOP3 推荐的问题信号全部换成了真实成因：
  | # | 影响占比 | 修正前（错） | 修正后 |
  |---|---|---|---|
  | 1 | 12.6% | SELECT * 取全字段 | **单次取数过大（约 11,000 行）；外层分页（ROWNUM 截断）** |
  | 2 | 10.9% | SELECT * 取全字段 | **超长 IN 列表（999 个字面量）；外层分页（ROWNUM 截断）** |
  | 3 | 9.4% | 耗时偏高但特征不突出 | **运行时建索引** |
- 20 个真实模板上的判据验证：误报 0 条，「无硬信号」的模板正确落到耗时形态判断。

### 说明

- 本版只改**判读口径与文案**，不改解析与统计逻辑 —— 所有计数、耗时、还原率与前版完全一致。
- 排序依据仍是**影响占比**（该模板累计耗时 ÷ 全部语句总耗时）。本版把理由写进了报告正文：
  衡量 SQL 代价最理想的指标是**逻辑读**（buffer gets），但达梦的 SQL 日志不记录逻辑读，
  只能退而用「**执行次数 × 平均耗时**」作代理 —— 它同样反映"这条语句总共让系统忙了多久"。
  按单条最慢排会把"一天只跑 1 次"的语句排前面；按次数排会把 5ms 的高频查询排前面 —— 都不对。

  > 为什么需要：5.4 GB 的 tar.gz 解压后 107 GB，单是解压就要 1 分钟以上，
  > 期间没有任何输出 —— 用户分不清"在跑"和"卡死"。
- ⚠️ **时间段筛选（`-f` / `-t`）现在同时决定「统计口径」**，不再只是筛选导出哪些 SQL。
  - 这解决一类真实场景：**只想看业务高峰、把夜间报表跑批排除掉**。
    以前的报告正文（语句类型分布 / 最耗时模板 / 热表 / 耗时分布）全都是全天数据，
    夜间跑批会把排名整体带偏，看不出高峰时段的真实问题。
  - 实测：`-f 00:43 -t 00:44` 后，命中语句 2,116 → 159，**语句类型分布同步收窄**
    （CAL 1224→105、SEL 367→18），P99 从 29.86s → 1.32s。
  - 报告头部新增**「统计时间窗口」**并在非空时用醒目色标出（HTML / Markdown / 终端），
    同时注明"窗口外 N 条已排除" —— 避免读者把窗口数据当成全天来判读。
  - 其余筛选（`-k` / `-m` / `-M` / `-u` / `-x` / `-l`）**行为不变**，仍只影响输出、
    统计保留全貌；`-E` 排除本就不入统计。设计理由见 `设计与选型说明.md` §9.5。
- **纯时刻写法** —— `-f 09:00 -t 18:00` 表示「**每天**的这个时段」，跨多天日志时不必逐个打日期。
  需成对使用（只给一边语义会退化成"所有天 00:00 之后"，故直接报错提醒）。
- **「优先优化推荐」**（HTML 报告新增一节，终端与 Markdown 同步）——
  像 Excel 交付件一样按**影响占比**给出该先改哪条，但比 Excel 更进一步：
  除占比外还给**问题信号**与**建议动作**。
  - 信号取自可从日志/SQL 文本确证的特征，不做无依据的猜测：
    `SELECT * 取全字段` / `SELECT 无 WHERE（疑似全表扫描）` / `前导通配 LIKE（索引失效特征）` /
    `高频轻量（次数极多、单次很快）` / `偶发极慢（存在长尾）` / `单次即慢` / `显著慢于同类`。
  - 优先级阈值与 Excel 交付件完全一致（≥10% 优先、3%~10% 次之），**占比分母统一**为
    全部语句总耗时 —— 同一模板在 HTML 与 Excel 里是同一个数（详见"修复"）。

### 改进 / 实测

- 🚀 **超大压缩包性能：5.44 GB tar.gz（解压后 107 GB）338 s → 214 s（1.58×）**。
  四步优化，全部实测验证：
  1. **gzip 读缓冲**（贡献最大）：`gzip.NewReader` 直接吃 `*os.File` 时，flate 每次只向
     底层要 **512 字节** —— 107 GB 会触发约 **2 亿次**系统调用。加一层 4 MB `bufio` 后，
     同一份数据的解压从 **161.7 s → 60.2 s（2.7×）**。
  2. **惰性参数解析**：现网日志 **98.4% 的行是 `PARAMS` 行**（1.08 GB 单文件里 420 万条），
     但真正需要参数的执行行只有 **493 条**（0.012%）。原实现对每条 PARAMS 都构造
     `[]Param`（堆分配 + 字符串切割），99% 的结果推进缓存后从未被读取。
     改为「先只数参数个数、内容延迟到真正命中时才解析」。
  3. **整数键参数缓存**：`p.key()` 原先把会话块拼成字符串做 map 键（concat + 哈希 + 分配），
     pprof 显示它连带 `mapaccess`/`mapassign` 吃掉 >25% CPU。会话块里的 `sess` / `thrd` / `stmt`
     都是十六进制地址，改为直接解析成 `uint64` 混合键（实测 100 万行只有 178 个唯一句柄，
     哈希退化成一次乘法）。**语义与原字符串键严格等价**，由回归测试兜底。
  4. **单次扫描取字段** + 省掉每行重建 `[]byte("sess:")` 的开销。
  - 单文件解析吞吐：**373 → 586 MB/s（1.57×）**；`-j 4` 时 1,074 → 1,797 MB/s。
  - 回归基线逐项一致（2,402,022 / 134,395 / 98.60%），且 **2.245 s → 2.011 s**。
- **进度条分母用自适应压缩比** —— tar.gz 没有索引、拿不到解压后总量。
  不用写死的估算系数（DM 日志压缩比实测 19.7×，写死 8× 会明显偏低），
  而是给 gzip 挂一个计数 reader 实时算「已解压 / 已读压缩」比例再外推，
  头几十 MB 后就相当准。

### 修复

- 🩸 **优化推荐的「影响占比」在 HTML 与 Excel 里不一致**。根因：占比分母取的是
  "当前视图里模板耗时之和"，而 HTML 视图按 `-p`（默认 20 条）截断、Excel 视图按
  `excelTop`（默认 50 条）截断 —— 两个分母不同，同一个模板算出两个占比
  （实测 18.6% vs 12.6%）。交付件与自看报告打架，开发商一眼能看出来。
  改为统一取**全部语句总耗时**（`TotalExecMS()`），三处口径一致。
- 修正 Excel 概览里"`-k/-m/-u/-x/-l/-f/-t` 只影响导出哪些 SQL；统计仍反映日志全貌"
  这句说明 —— V2.5 起 `-f/-t` 例外，已按新语义改写。

### 说明

- 本次新增了一个隐藏诊断开关：设环境变量 `DMSQLQ_CPU_PROFILE=<文件路径>` 可导出
  Go CPU profile（本次的四步优化就是靠它定位的）。日常使用无需关心。
- 本版新基线仍为 15 文件 / 2.0 GB（DMSERVER 20260928），但性能对照用的是
  5.44 GB 现网 tar.gz（中垦乳业 KD1 日志，100 个文件、解压后 107 GB），
  因为它才能暴露压缩包路径的问题。

## V2.2 — 2026-09-28

**亮点：报告「瘦身」—— 排行榜一律 ≤20 条，负载分布从上千行表格换成一张图**

> 这一版来自一次真实演练：换另一套现网日志（`dmsql_DMSERVER_20260928_*`，15 个文件 / 2.0 GB /
> **UTF-8** 编码）跑完整流程，发现报告有两处"读不动" —— 排行榜动辄 200 行、负载时间分布逐时段列出
> 80+ 行表格；同时挖出两个会打印 `%!(EXTRA …)` 的格式串缺陷，以及一个**交付件只出「概览」**的严重缺陷。

### 新增

- **报告新增「错误码分布」小节**（HTML / Markdown / 终端 / Excel 概览 四处都有）

  原来错误码只统计不展示，只在判读提示里用到一条 —— 而这次演练正好证明它必须露出来：
  该库 1.36 小时内有 **4,581 条 `[ERR(-608)]`**，看着只占 3.4% 次数，却吃掉 **79.7 小时**
  执行耗时（占 **74.9%**）—— 每条都要等满超时阈值，平均 63.5 秒。**只看次数根本发现不了。**

  表格把「次数 / 占 [ERR] 次数 / 累计耗时 / 平均」并列，就是让"次数不多却极耗时"这类错误码现形。
  并附官方口径提醒：`-608` 是「会话请求超时 / 锁超时」，**它本身只说明超时，不能单凭它断定就是锁等待** ——
  要定性需在库上核对 `V$TRXWAIT` / `V$LOCK`，或让采集侧 `SQL_TRACE_MASK` 补上 29，由日志直接记录锁等待。

- **负载时间分布改为按时间的图**（HTML 内联 SVG）

  时段不多（≤150）画**柱状图**、时段多改画**折线带面积**；峰值时段标红、悬停看该时段明细；
  空时段留白（业务低峰 or 采集中断，一眼可分）。仍是**单文件零依赖**：直接内联 `<svg>`，不引任何图表库。
  终端与 Markdown 用一行 **sparkline 字符图**（`▁▂▃▄▅▆▇█`）表达同一形态。

- **`-p` 调大即可导出完整清单**

  `-p` 的语义收敛为「导出件（Excel）的行数」：默认 20，`-p 200` 就出 200 行的完整清单，
  而报告这边**不再跟着变大**。

### 改进

- ⚠️ **报告里各排行榜一律最多显示 20 条**（原来是 `-p` 给多少显示多少）

  报告是"给人看结论"的：榜单/时段一长就没人读，还把真正的结论冲散。
  现在 `-p` 只放大交付件，报告恒 ≤20（`-p` 更小时按 `-p` 走）。
  要完整清单用 `-e 交付.xlsx -p 200` —— 那才是"要完整"该用的地方。

- ⚠️ **`-p` 默认值 10 → 20**；并取消"Excel 模式下把行数悄悄提到 200"的行为。

- **「吞吐与时轴」与「负载时间分布」两节合并**：指标表 → 时间图 → 高峰时段 Top20，不再分散在两处。

- **Markdown / 终端的逐时段完整表已移除**，只留趋势图 + 高峰榜（完整时间轴见 Excel 的「时段分布」工作表）。

### 修复

- **交付件只出一张「概览」**（严重；仅当报告与交付件的行数不同时触发）

  根因：`writeFullSQL()` 内部会调 `releaseStats()`，把聚合表（`Tpl` / `ByOp` / `ByTable` / `Slow` / `Locks` …）
  全部置 nil —— 目的是让随后的**二次扫描**不被 GC 拖慢。而 V2.1 新增的"交付件视图"恰好建在它**之后**，
  于是拿到的是空聚合，除「概览」外一张表都出不来。
  **显式给 `-p` 时两边行数相同、根本不建第二个视图，正好绕过这个坑**，所以只在默认参数下暴露 ——
  也提醒：这类"只在默认路径上出现"的缺陷，必须按默认用法跑一遍才能发现。
  现已把交付件视图移到 `writeFullSQL` 之前。

- **`-S` 终端报告「热表」表头打印成 `%!(EXTRA string= 耗时占比)`**（V1.x 起就有）

  `fmt.Fprintf` 的格式串只写了 7 个 `%s`，却传了 8 个参数 —— 结果是表头少一列、且与数据列整体错位。

- **`.full.sql` 事务分组注释头打印成 `%!(EXTRA …)`**

  `语句 %d 条` 配的是 `fmtInt()` 返回的字符串（带千分位），占位符应为 `%s`。

  → 两个格式串缺陷都由 **`go vet`** 自动揪出。**本版起把 `go vet` 纳入发版流程**：
  此前只做"编译 + 回归"，而 `%d`/`%s` 配错这类问题编译期完全查不出来，只会在输出里留下乱码。

### 实测

- 新基线（现网 `D:/dmsql_log` 的 `dmsql_DMSERVER_20260928_*`，15 个文件 / 2.0 GB / UTF-8）：
  记录 **2,402,022** / 命中 **134,395** / 参数还原 **98.60%** / 耗时 **4.4 s（827 MB/s）**；
  报告 TopN 全部 ≤20；SVG 图 83 根柱 + 83 条悬停提示；交付件 9 张工作表、`SQL优化清单` 20 行、
  `时段分布` 完整 83 个时段。
- ⚠️ **回归基线变更**：原 `D:\dmsql_log\dmsql_KD1_*`（1 GB / GBK）已被日志轮换清理，
  本机现换成上面这套 DMSERVER 日志（UTF-8）。回归数字请以新基线为准。
- 该日志的采集侧**未开掩码 29**：无锁等待、无 COMMIT/ROLLBACK 事件（报告里「采集配置体检」会提示）；
  却也正因此说明「错误码分布」这条通道的价值 —— 锁的问题看不到时，超时错误码仍会留下痕迹。
- 交付件自检（openpyxl 严格回读）全通过；HTML 图表用 Chrome 无头截图肉眼确认。

- **`-e, --excel FILE`：生成 Excel 交付件（.xlsx）**

  | **SQL优化清单** ★ | **开发商** | 语句模板按**累计耗时降序**，带执行次数 / 平均 / 最大 / **占总耗时** / **优先级** / 样例 SQL |
  | **慢SQL明细** | 开发商 | 最慢 N 条逐条列全：时间、耗时、类型、行数、用户、EXEC_ID、来源日志、完整 SQL |
  | **热表** | 开发商 | 表名、语句数、读/写次数、读写比、累计耗时、耗时占比 → 索引设计的依据 |
  | **语句类型分布** | 双方 | 各类型的次数占比 vs 耗时占比（找出「次数不多但很慢」的那类） |
  | **锁等待** | 双方 | 指标 + 等待时长分布 + 最久等待明细（等待方/持有方 trxid 与用户）+ 被争抢的表 |
  | **长事务** | 双方 | trxid、跨度、SQL 执行耗时、**利用率**、语句数 + 每事务语句数分布 |
  | **时段分布** | 双方 | 按分钟/小时/天的时间桶：SQL 数、QPS、耗时、COMMIT/ROLLBACK、占比 |
  | **用户与客户端** | 双方 | 用户排行 + 客户端排行（定位「是哪个应用在压库」） |
  | **结构变更与高危操作** | 双方 | 最慢语句涉及对象的最近一次 DDL、高危操作、结构变更时间线 |

  **「SQL优化清单」的优先级规则是透明的**：该模板累计耗时 ÷ 本次语句总耗时，
  ≥10% 记「优先」、3%~10% 记「次之」、其余「一般」—— 规则写在表底的说明行里，
  开发商能看到这个判断是怎么来的，不用猜。

- **Excel 里是「真数字」，不是文本**

  所有数值单元格写的是 `<v>` 数值而不是字符串，所以在 Excel/WPS 里可以直接**排序、求和、
  画图、写条件格式** —— 开发商想按「平均耗时」再排一次，或只筛「次数 > 100 且最大 > 1s」，
  都不用先做分列转换。

  | 处理 | 做法 | 为什么 |
  |---|---|---|
  | 数字 | `<v>` + 数字格式（`#,##0.00` / `0.0%` / `0.00%`） | 保持可计算 |
  | 文本 | `inlineStr`（不建 sharedStrings） | 少一层间接，写出更简单、更不易错 |
  | 换行 | `xml:space="preserve"` + 自动换行 | 多行 SQL 在单元格里保留原格式 |
  | 列宽 / 表头 / 冻结 / 筛选 | 逐表设置 | 打开就能按列筛选，表头滚动不消失 |

- **零依赖实现**：`.xlsx` 本质是一个 zip 包，里面装几段 XML。用标准库 `archive/zip`
  ＋手写 OOXML 生成，**没有引入任何第三方库** —— 继续守住「单文件、零依赖、离线、
  信创可跑」这条线（这也是这一版唯一值得"多写代码"的地方）。

- **Excel 模式下 `-p` 默认 200 行**

  HTML 是「看一眼」，10 行够用；交付件是「拿去改」，10 行不够。
  Excel 模式下未显式给 `-p` 时自动取 **200**；**给了 `-p` 就一字不改地照办**。

### 改进

- **`-e` 与 `-s` 的屏幕行为对齐**：只给 `-e` 时也打简要结论（含交付件路径），
  但**不把 SQL 写到 stdout** —— 用户此刻的目标是「拿到文件去发」，不是「在屏幕上读几十万条 SQL」。
  确实想连 SQL 一起导，显式加 `-o all.sql`。

- **配套 `.full.sql` 跟着 `-e` 一起出**：文件名取交付件主名（`交付.xlsx` → `交付.full.sql`），
  里面是 TopN 语句与相关事务的全部语句，可直接整批拿去 disql。

- **落盘提示词随格式变化**：`-r 报告.xlsx` 不会再提示「HTML 浏览器直接打开」。

### 修复

- **`-h` / `--help` 把整篇帮助打印了两遍**（V2.0 及更早都有）

  Go 的 `flag` 包遇到未定义的 `-h` / `--help` 时，会**先自己调用一次 `Usage`** 再返回 `ErrHelp`；
  而代码里又调用了一次，于是整篇输出重复（实测 164 行 × 2 = 328 行）。现在只打一遍。

  记录 **3,347,484** / 命中 **467,964** / 参数还原 **97.76%** / 锁等待 **54** 次 —— **逐项一致**。
- 交付件自检（`test_xlsx.py`，用 openpyxl 严格回读）：10 张工作表齐全、表名合法无重复、

  **全文无 XML 非法控制字符**。

## V2.0 — 2026-09-22

**亮点：按姊妹工具 `dmmem-go` 的设计思想重做「交付体验」** —— 报告生成后自动打开浏览器、

> `dmmem-go`（同目录 `..\DMMemGo\`）是这批工具里的「极简版」，它把「降低使用门槛」

### 新增

- **⚠️ 生成 HTML 报告后自动用默认浏览器打开**（Windows / macOS / Linux 都支持）

  以前 `-s` 跑完只打印一行路径，用户还得自己去目录里找那个文件。现在报告一落盘就顺手打开，
  `dmsqlq . -s` 才是真正意义上的「一条命令看到结果」。

  | 平台 | 打开方式 | 备注 |
  |---|---|---|
  | Windows | **`explorer.exe <文件>`** | 不用 `rundll32 url.dll,FileProtocolHandler`，见下 |
  | macOS | `open` | |
  | Linux | `xdg-open`，没有则退到 `gio open` | 桌面发行版优先 |

  **为什么 Windows 不用 `rundll32`**：它是公认的 LOLBin（可被用来执行任意代码），
  **不少企业 EDR 会直接拦掉** —— 本机开发沙箱这次就把它拦了（报为黑名单程序），

    无桌面环境（SSH / 无 DISPLAY）下**静默跳过、不往终端吐噪音**。

- **`-Q` / `--no-open`：关掉自动打开**

  批处理里连着跑十几份日志时，弹一屏浏览器窗口是很烦的：

  ```bash

- **无参数运行时的「下一步」引导**

  以前无参数只打一屏帮助（138 行），现在帮助之后**顺手看一眼当前目录**，
  有日志就把命令写好给你抄：

  ```

      dmsql_KD1_20260910_000221.log

  目录里没有日志时，也会给一条最朴素的例子（`dmsqlq /dmdata/log -s`）。

- **终端简要统计补了一张「最慢语句 TOP5」表**

  以前简要版只有几行要点，截图反馈时对方看不到「最慢的到底是哪几条」。现在补一张等宽对齐的

  完整 TopN 与可点击展开的 SQL 仍在 HTML 报告里 —— 终端只负责「够截图」。

- **交付包新增 `CHECKSUMS_V2.0.txt`（md5 清单）**，拿到包可以先核对完整性。

### 改进

- **Windows 双击 exe 不再「一闪而过」**：无参数运行时若输出连着终端，会等一次回车再退出

## V1.9 — 2026-09-20

**亮点：报告从"能看"进化到"能拿走"** —— 点一下表头，整类 SQL 就下载成一个可直接跑的
`.sql` 文件；同时把上个版本堆在一起的交互按钮做了减法，界面回到干净状态。

### 新增

- **每张表一个「导出全部 TopN」按钮**（最慢语句 / 最耗时模板 / 高危操作三处）

  按钮在表格上方，点一下把**该表所有行**的 SQL 拼成一个 `.sql` 下载，文件名直接说明内容
  （`slow_top10.sql` / `template_top10.sql` / `danger_top4.sql`）。导出格式：

  ```
  -- [#1] 58.37s  00:01:28  用户 COSMIC_FI  行数 100
  SELECT A.fcostaccountid "costaccount", ... WHERE ...;
                                                 ← 空行分隔
  -- [#2] 50.16s  00:01:06  用户 COSMIC_SYS  行数 500
  DELETE FROM t_isc_sf_proc_log WHERE ...;
  ```

  三个设计点值得说：

  | 设计 | 为什么 |
  |---|---|
  | **注释头分隔** | `--` 是 SQL 行注释，整个文件仍是**合法 SQL**；同时每条都能看出是哪条（按 `#n` 与表格序号一一对应） |
  | **语句压成单行** | 换行、连续空白、行尾分号统一处理，**不折行**，粘进 disql、丢进 `grep`、贴工单都不会散架 |
  | **每类一个文件名** | 一眼看出"这是最慢的 10 条"，不会和模板样例、审计清单混在一起 |

  实现上把数据放在 `<script type="application/json" class="expdata">` 文件块里：
  浏览器不执行、不显示，与页面布局互不干扰；也不需要把几万字符的 SQL 塞进 `data-*` 属性
  再和转义规则较劲。

- **`.full.sql` 附件与它并存，各有分工**：附件是"**跨节整批**"（含长事务与锁等待涉及事务的
  全部语句，按事务号分组），表头按钮是"**本表同类**"（点一下就拿到、不用翻文件）。
  日常"想拿最慢那 10 条去复现"直接用按钮，不必再开附件。

### 改进

- **去掉重复的 `[展开]` 按钮** —— 点击摘要文字本来就能展开，两个入口做同一件事，
  留一个更清楚。现在展开方式只有"点文字"一种，按钮列只保留 `[复制]`。
  按钮少了、列宽也松了，长语句的可读面积更大。

- **去掉逐行 `[存为 .sql]` 按钮**。上个版本给每一行配了"单条另存"，
  实际用起来**又占地方又丑**，而真实需求几乎总是"这一整类我都要"。
  于是换成表头的「导出全部」—— 想只要其中几条，展开后用 `[复制]` 更顺手。

- ⚠️ **`-s` / `-S` 语义重排**（会影响命令行习惯，请留意）

  | 命令 | 之前 | 现在 |
  |---|---|---|
  | `dmsqlq <日志>` | 输出 SQL | 不变 |
  | `-s` | 出统计（写文件）+ 屏幕简要 | **强制出报告**（文件名自动取 `<日志名>_报告.html`），屏幕只给简要要点 |
  | `-S` | 同 `-s` 但只算不导 | **命令行简要统计**：不出文件、不导 SQL |
  | `-s -o x.sql` | — | 报告 + SQL 一起要（SQL 进 `x.sql`） |

  理由：报告做好之后，`-s` 会变成**最高频**的用法。既然用户已经明确要报告，
  核心目标就是"看报告"，不该再逼他多打一个 `-S` 才能同时出文件。
  于是 `-s` 直接等于"出报告"，而"只想在 SSH 里扫一眼"这种轻量需求交给 `-S`。

- ⚠️ **`-s` 不再把几十万条 SQL 刷到屏幕上**。以前 `-s` 会把 SQL 全打到 stdout，
  屏幕上几百 MB，既把统计结论冲散，也**没法接管道**（`| grep`、`| head` 全废）。
  现在：不带 `-o` 时 `-s` 完全不往 stdout 写 SQL；真想要 SQL 就显式 `-o 文件名`。
  `stdout` / `stderr` 分工也随之理清 —— **报告路径、统计要点走 stderr，SQL 才走 stdout**。

- **不带任何参数仍是纯帮助**（138 行用法），不跑解析、不刷统计，行为未变。

### 修复

- **导出内容退化成 `-` 与 `S`**：`expJSON` 起初把数据编成扁平数组 `[头,SQL,头,SQL,…]`，
  而 JS 侧按 `rows[i][0] / rows[i][1]` 取值 —— 于是 `rows[i]` 是字符串、`[0]` 只取到首字符，
  导出的文件全是 `-` 和 `S`。改为输出**二维数组** `[[头,SQL],…]`，与 JS 取值方式对齐，
  并在两侧注释里写明"改一处必须同步另一处"。

- **⚠️ `-s -r 报告.html` 仍会把 140 万行 SQL 刷到屏幕**：`wantSQL()` 的判断条件写成了
  "报告路径为空才不输出 SQL"，于是**一旦给了 `-r` 文件名，抑制就失效** ——
  正好和"出报告时屏幕要干净、要能接管道"的初衷相反。
  改成判断"**有没有给 SQL 的去处（`-o`）**"，与报告路径解耦。修复后实测：

  |---|---|
  | `-s`（自动命名报告） | **0** |
  | `-s -r 报告.html` | **0** |
  | `-S` | **0** |
  | `-s -o all.sql` | **0**（SQL 进文件） |
  | 默认（无 `-s`） | 1,404,543（照旧全出） |

## V1.7 — 2026-09-19

**亮点一：审计与恢复定位** —— 误删表/误删数据、权限被改、批量 UPDATE 打错条件，
事后要回答"谁、什么时候、对哪个对象、影响多少行、能不能恢复"，这一版把答案放在同一张表里。
**亮点二：六个"低成本高判读价值"的统计项**（分位数、每事务语句数分布、读/写比、
EXEC_ID 下钻、DDL 首词、结构变更时间线）全部落地。

### 新增

- **审计与恢复定位（新报告节 + 附件第 4 部分 + `-d` 过滤）**

  识别这些操作，时间倒序一条条给出：`DROP TABLE/INDEX/VIEW/USER/SCHEMA…`、`TRUNCATE`、
  **无 WHERE 的 DELETE / UPDATE**、`GRANT`/`REVOKE`、`CREATE|ALTER|DROP USER`、
  `ALTER … DROP COLUMN/PARTITION/CONSTRAINT`、**大批量 DML**（DELETE ≥1 万行 / UPDATE ≥5 万行）。

  **`[ORA]` 行终于有了用处**：它是"语句已到达服务器并完成语法解析"，但可能**没执行成功**
  （权限不足、超时、客户端取消、事务回滚）。桌面版把 `[ORA]` 排除在统计外、Web 版默认整个丢弃 ——
  可对审计来说，"有人试图删这张表"本身就是证据，所以这一类也留在清单里并标注 **仅解析未执行**。
  实现上按语句句柄把 `[ORA]` 与执行行配对：合并成功就是完整链路（含影响行数、EXEC_ID），
  没有执行行就保留为"仅解析"。

  **恢复定位四要素**：时间点 / 对象 / 操作人（用户 + 客户端 + **线程**）/ **提交 LSN**。
  LSN 来自 `TRX: COMMIT LSN[…]`，按 30 秒一桶降采样（现网提交是百万级，全留会吃内存），
  出事后可以直接给出"该时刻前后最近的提交 LSN"作为不完全恢复的锚点。
  另附**被反复操作的对象**摘要，与**结构变更时间线**（`CREATE`/`ALTER`/`RENAME`/`COMMENT ON`，
  环形保留最近 4000 条 + 类型统计）。

  `-d/--danger` 可以只导出审计命中的语句（`dmsqlq . -d -N -o danger.sql`），单独归档或复核。

- **分位数 P50 / P90 / P95 / P99**：全局、按语句类型、按用户三处都给了。
  用**对数分档直方图**（160 档，每档 10^(1/16)，覆盖 1µs~1000s）算，桶内插值误差 <2%；
  3 亿条记录也不涨内存（每维度 1.28KB），比"排序取分位"现实得多。
  意义：平均 5ms、P99 800ms 说明"少数语句在拖后腿"，只看平均/最大是看不出来的。
- **每事务语句数分布**：1 / 2-5 / 6-20 / 21-100 / 101-1000 / >1000 六档 + 中位数。
  批量导入慢的头号原因不是"某条 SQL 慢"而是**逐条提交** —— 实测某现网库
  **71.8% 的事务只有 1 条语句**，这就是证据。
- **热表读/写比**（读次数 ÷ 写次数）：读多写少却慢的表通常缺索引。
- **`EXEC_ID` 抓取与下钻指引**：最慢语句表新增 EXEC_ID 列，并给出可直接复制的
  `SELECT * FROM V$SQL_NODE_HISTORY WHERE EXEC_ID = <id>;` —— SQL 日志没有逻辑读，
  但拿 EXEC_ID 去库里就能换回每个执行节点的 `TIME_USED`（其中 `DLCK` 节点正是
  日志里 `DLCK used time:N(us)` 的来源）。
- **DDL 首词分布**（写进采集配置体检）：很多库的 `[DDL]` 其实不是改表结构。实测某现网库
  `[DDL]` 占 6.3% 次数却占 **68.4% 耗时**，首词一列出来就清楚了：`STAT 58,719 次`（更新统计信息）
  + `TRUNCATE 4 次`。排慢查询时应当先把 `STAT` 排掉再看业务 SQL。
- **慢语句对象 → 最近一次结构变更**：性能劣化常紧跟一次 DDL，报告在慢语句小节后直接列出
  "这条慢 SQL 的表最近被谁改过"。

### 改进

- ⚠️ **长事务表的"语句数"口径修正**：`TRX: START` 是**事件不是语句**，之前被计入，
  导致每个事务的语句数整体 +1（"1 条语句的事务"这一档会凭空消失）。修正后
  长事务的语句数与"每事务语句数分布"才是真实值。
- **审计采集与统计一样放在筛选之前**：一条被 `-m 1000` / `-k SEL` / `-n 100` 过滤掉的
  `DROP TABLE` 也照样进审计清单 —— 那恰恰是最不该漏的。
- 审计热路径做了免分配处理（每行一次字符串分配 → `[]byte` 前缀比较、`ParseInt` 前置短路），
  与 V1.6 的 A/B 对比整体开销 **+5%**（1GB 日志只统计 6.9s → 7.3s）。
- 帮助文本、报告节清单同步更新。

## V1.6 — 2026-09-19

**亮点：解析判据与官方 Web 版实时解析工具（`sql_realtime_parse_tool` v1.5.3）逐条对齐** ——
这一版改的都是"**看得见却看错**"的地方：时间戳精度、耗时单位、锁等待格式。
依据是本机的《DM8 SQL 日志内容解析学习笔记》（对照桌面版 DmLog 8.183 与 Web 版 v1.5.3 两份反编译）。

### 新增

- **采集配置体检（报告新增一节）**：据日志实际内容反推 `sqllog.ini` 开了哪些位，逐条给出结论与改法。

  | 检查项 | 日志里看到什么 | 结论 |
  |---|---|---|
  | 时间戳精度 | 毫秒 / 微秒 | 6 位微秒时间戳本工具同样支持 |
  | 执行行耗时覆盖（掩码 24/25） | 100.00%（x/y 行带 EXECTIME） | 缺耗时的是哪一类 |
  | 参数行 PARAMS（掩码 28） | 0 行 / N 行 | 没参数不是解析问题，是掩码没开 |
  | 事务事件 / 锁等待（掩码 29） | 0 行 / N 次 | 长事务、TPS、锁等待都依赖位 29 |
  | `[ORA]`（27）、`[LGN]`（31）、`[ERR(...)]`（23） | 0 行 / N 行 | 要这些能力就得开对应位 |
  | EXECTIME 单位 | 毫秒 (ms) / 微秒 (us) | 对应 `EXECTIME_PREC_FLAG` |

  同时把这段结论写进「判读提示」——**"分析不出锁等待 / 没有参数"的第一嫌疑是采集配置，不是解析器**。
- **长事务新增「SQL 执行耗时」与「利用率」两列**：利用率 = 事务内 SQL 累计执行耗时 ÷（事务跨度 + 首条 SQL 耗时）。
  **利用率低 = 占着事务不干活**（长时间持锁、应用侧忘了 commit/rollback），这类事务比"SQL 慢"更该先处理。
  跨度 ≥60s 且利用率 <20% 时，「判读提示」会点名指出并给出溯源命令。
  （口径取自官方 Web 版 jar 内的 SQL 模板「事务的SQL」，比单纯看跨度更能定位问题。）
- **报错语句的错误码分布**：`[ERR(-2111)]` 里的错误码单独抽取并在体检节里给出最多的一种。
  官方桌面版不提取错误码，但"哪个错误码最多"是排查的第一手线索。

### 改进

- ⚠️ **耗时单位不再写死 `(ms)`**：`EXECTIME` 的单位由 `sqllog.ini` 的 `EXECTIME_PREC_FLAG` 决定
  （`0`→毫秒、`1`→微秒）。本工具现在**读单位并统一换算成毫秒**，`(us)` / `(ns)` 都认。
  之前如果拿去分析 `EXECTIME_PREC_FLAG=1` 的库，**耗时会整体差 1000 倍**（例如"1.5 秒"显示成"1.5 毫秒"），
  且报告里毫无提示。现在报告会明示单位，**不同单位的库可以横向比较**。
- ⚠️ **锁等待判据从 1 种格式扩到 3 种**（与官方 Web 版一致）：
  ① `trx[N] LOCK_TID (mode:X, table id:T, tid[..]) wait used time:N(ms)`；
  ② `trx[N] LOCK_TID (mode:X, table id:T) wait for K trxs, trx[a, b] used time:N(ms)`（现网主流）；
  ③ 老版本 `trx[N] wait for LOCK_TID (mode:X, table id:T, tid[..]) used time:N(ms)`。
  三种格式的 `used time` 都吃 `(ms|us|ns)`。
  另外：持有方列表带 `...more`（日志侧截断）时会剥离并单独计数；"声明被等事务数 ≠ 实际列出数"会告警。
  **本机 7.3GB 现网日志实测 1,375 行 `LOCK_TID`，命中率 100%（全部是格式 ②）**。
- **时间戳判据对齐官方 Web 版**：合法时间戳 + **紧跟 `" (EP["`** 才算新记录；
  小数位只接受 **3 位（毫秒）或 6 位（微秒）**。
  这挡住了"参数值里带换行的伪时间戳续行"（如 `2026-09-09 23:54:15:015#1200` ——
  第 20 位是 `:` 不是 `.`）—— 宽松判据会把一条 SQL 劈成两三条。
  **本机 26,799,837 条合法时间戳行里，"后随不是 ` (EP[`"的有 0 条**，说明这条判据充分且必要。
  **兼容性**：老版本 DM 日志（无 `EP[n]` 段）与 `SVR_LOG=3` 简单模式的日志会自动切回宽松判据，
  不会因为收严而解析不出来（官方 Web 版在这里会整篇退化成一条续行，本工具做了自适应）。
- **参数还原改为两级匹配**：先按**严格键**（会话块含 `thrd`/`user` + 语句句柄）找，
  找不到再退到**句柄键**（只有 `stmt`，官方 Web 版 v1.5.3 的默认策略）。
  线程漂移（同一条 SQL 的解析与执行落在不同线程）时严格键会失配、句柄键仍能命中 ——
  官方桌面版只有第一级，因此会留下一批本可还原的 `?`。报告体检节会显示靠句柄键兜底还原了多少条。
- **热表提取更干净**：
  - 跳过**字符串字面量**与 `--` / `/* */` 注释 —— `where msg='delete from t_tmp'` 不再造出假表名；
  - 跳过 **CTE 名**（`WITH a AS (...), b AS (...)` 里的 `a`/`b` 不是物理表），与官方 Web 版 `SqlTableExtractor` 一致。
- **行数缺失显示 `-`**：`ROWCOUNT` 在日志里本来就不存在的（`[DDL]`、`[CAL]` 一律不带行数）显示 `-`，
  不再显示 0 或空 —— 避免读成"这条 DDL 影响了 0 行"。
- 帮助文本与报告说明同步更新；报告「语句类型分布」下的耗时占比说明、热表口径说明都补齐了单位与过滤规则。

### 修复

- **6 位微秒时间戳（`yyyy-MM-dd HH:mm:ss.SSSSSS`）整篇解析失败**：老代码按"固定 23 字符"取时间戳，
  遇到 26 字符的时间戳会把第 24 位（微秒的第 1 位）当成会话块的分隔空格，
  于是**整个文件被当成一条超长续行**，输出 0 条。现已按长度自适应（`tsLen` 返回 19/23/26）。
- **`SVR_LOG=3` 简单模式的语句会被丢掉**：这类行没有会话块，而 SQL 里常自带括号
  （`insert into t values(1)`），老代码把 `values(1)` 误当成会话块，整行走了"非 SQL 事件"分支。
  现在要求**会话块必须紧跟时间戳**，简单模式改用 `-L` 能正确逐条输出。
- **`trx[N] alloc pseg page[...]` 白跑正则**：这类行以 `trx[` 开头但根本不是锁事件
  （本机现网 115,380 行），现在入口先判 `LOCK_TID` 再进正则，省掉这批无效匹配。
- 锁等待格式③的持有方是 **tid 列表（线程号）**，之前会显示成 `trx[1, 2]` 误导为事务号，现在标为 `tid:1,2`。
- 热表文本报告的表头多印了一列"耗时占比"（列错位）。

### 实测（2026-09-19，本机 12 个现网 dmsql 日志）

| 项目 | 数值 |

## V1.5 — 2026-09-19

**亮点：报告负责"好看"，附件负责"能查"** —— 报告里的 SQL 仍是摘要，但每条都能溯源到完整语句；
锁等待补齐"谁在持锁、锁在哪张表"；负载统计从"秒"改为按分钟/小时/天看高峰。

### 新增

- **完整 SQL 附件（`-F` / `--full-sql`）**：用 `-r` 出报告时，同名目录下会多一个
  `报告名.full.sql`，内含三部分：① 最慢语句 TopN、② 最耗时模板 TopN、
  ③ **长事务与锁等待涉及事务的全部语句**（按事务号分组，带注释头、参数已还原）。
  报告里只显示摘要，要看全文就打开附件 —— 两全其美，不必牺牲排版。
  写 `-F off` 可关闭；`-F 文件名` 可改名。
- **负载时间分布**取代原来的"最繁忙的秒 TopN"：粒度**按日志跨度自适应**（≤2 小时按分钟、
  ≤3 天按小时、更长按天），给出「高峰时段 TopN」（含平均 QPS、COMMIT/ROLLBACK、条形图）
  与完整时间轴（HTML/Markdown 里全部列出，空时段也保留，能看出采集断档）。
  秒级 TopN 被撤掉的原因：同一波高峰里秒与秒的差异是噪声，看不出"业务高峰"。
- **对象 ID → 表名映射（`-O` / `--obj-map`）**：DM 的 SQL 日志只记对象 ID、不记表名，
  锁等待里显示的就是 ID。把库上查出来的结果（每行 `ID=表名`，或直接粘贴 ID 与表名两列）
  存成 UTF-8 文件，加 `-O 文件名` 即可在报告里直接显示表名。
  文件没给时，报告会自动生成**可直接复制执行的反查 SQL**（`SYS.SYSOBJECTS`）。
- **锁等待明细补齐关键信息**：每条等待都给出「等待方 trxid + 用户」与「**持有方 trxid + 用户**」
  （回答"谁在持锁"—— 持有方用户靠"事务号 → 用户"反查，因为日志的锁行只带等待方会话信息）；
  每条附一行**溯源命令**，复制即可导出该事务当时在跑的语句。
  「被争抢的表」增加：**等待方用户**、**最长一次等待发生的时间**。
- **`-x` 支持多个事务号**（逗号分隔），如 `-x 101,102,103` —— 排查阻塞时常要一次看好几个。
- 长事务表增加**用户列**；长事务小节直接给出配套附件路径与 `-x` 抽取命令。

### 修复

- ⚠️ **报告/附件里的 SQL 现在与 `-o` 导出完全一致（参数已还原）**。
  之前报告里的最慢语句、模板样例存的是**原始带 `?` 的文本**，导致附件里出现"本可执行的语句却是 ?"。
  现在改为在参数还原成功后**回填**可执行版本（模板样例则在遇到能还原的样本时替换）。
- ⚠️ **负载时段桶数算错**：时区偏移在取模后被多减了一次，每个桶起点整体前移 8 小时 ——
  实测 11 个时段被算成 **491 个**。修正后时间轴与日志跨度一致。
- **V1.4 附件生成过慢**：二次扫描时，扫描期几百 MB 的聚合表还挂在内存里，
  GC 反复标记它们 —— 同一 1GB 日志的附件耗时从 **7.5s 压到 1.5s**（整体 3.6s → 5.1s）。
- **模板样例的 `?` 会误导人**：日志里该语句前确实没有 `PARAMS` 行（采集侧缺），
  不是解析失败。现在这类摘要会明确标注 **`[参数未还原]`**，并在小节里说明查掩码 28。
- "涉及对象数"改用总数（之前被 `-p` 截断后的条数显示，容易被误读成只有那么几张表）。
- 锁等待明细的列宽与截断调整（多持有方 `trx[a, b]` 会把表格挤错位）。

## V1.4 — 2026-09-19

**亮点：统计从"看总量"扩展到"看时间与对象"** —— 新增热表、QPS/TPS、客户端排行与排除模式，报告可出 HTML。

### 新增

- **语句类型分布加"耗时占比"与字符柱状图**：与"次数占比"并列显示。
  两者偏离大就是线索 —— 实测某日志 DDL 只占 6.3% 次数却占 **68.4% 耗时**。
- **热表 TopN**：从 SQL 文本提取表名（`FROM`/`JOIN`/`INSERT INTO`/`UPDATE`/`DELETE FROM` 等位置），
  给出语句数、读/写次数、累计耗时、最大耗时、耗时占比 + 条形图 —— 直接回答"该优化哪张表"。
- **吞吐与时轴（QPS / TPS）**：平均/峰值 QPS、平均/峰值 TPS（按 COMMIT）、回滚率、
  有事件的秒数、**最长静默空档**、**最繁忙的秒 TopN**。
- **客户端排行**（`appname @ IP`）：定位"是哪个应用/主机在压库"（生产日志 appname 常为空，此时按 IP）。
- **`-E` / `--exclude-op`（排除模式）**：剔除噪声后再看统计。
  两种写法自动识别：① 事件类型码（`CAL`/`DDL`/`SEL`…）；② 任意 SQL 子串（`ANALYZE`/`DBMS_STATS`/`TMP_`…）。
  例：`-E CAL,ANALYZE,DBMS_STATS` = 剔除调用类与统计信息收集。
- **报告支持 HTML 格式**：`-r 报告.html` 出单文件 HTML（KPI 卡片 + 条形图 + 全部表格），
  浏览器直接打开、`Ctrl+P` 可出 PDF。三种格式按后缀自动选：`.html` / `.md` / 其他纯文本。
- 判断提示新增：日志覆盖度自检、回滚率偏高、峰值与锁等待重合、热表集中、静默空档。

### 改进

- ⚠️ **`-E` 的语义与其他筛选不同**：`-f/-t/-m/-M/-k/-u/-x/-l/-n` 只影响"输出哪些 SQL"，
  统计仍反映日志全貌；而 **`-E` 的排除会同时把该批语句剔出统计**（它表达"这类语句不是有效负载"）。
  概览会单列 `已排除` 条数便于核对。
- ⚠️ **QPS 口径修正**：只统计有耗时的语句事件，**排除 `[ORA]`（只解析未执行）**，
  与"执行耗时分布"保持一致。同一日志平均 QPS 由 1635 修正为 **825** —— 之前的数值偏高近一倍。
- 热表表名统一大写并去 schema（`T_CAL_X` 与 `t_cal_x` 合并）；结果含字典视图与临时表，
  噪声可用 `-E USER_,DBA_,TMP_` 排除。
- 帮助文本更新：新增 `-E` 说明、报告格式说明、统计口径说明。

### 修复

- ⚠️ **锁等待漏报（影响统计结果）**：等待多个持有方时，日志写成 `trx[10130987610, 10130987611]`
  （逗号分隔的**列表**），旧版本只认单个数字，导致这类行被**静默丢弃** ——
  实测同一份 1GB 日志，等待数由错误的 **40 次**修正为真实的 **54 次**（漏掉 35%）。
- ⚠️ **"只见 START、未见结束"的事务误报**：`COMMIT`/`ROLLBACK` 行的 trxid 通常为 0、无法与 `START` 关联，
  旧逻辑据此判定"可能未提交"，实测在某日志上**误报 26 万个事务**。
  现在只在"日志里完全没有结束事件"时才给该提示，其余情况明确说明"无法判定单个事务是否已提交"。
- **热表表名提取三处错误**：① `SELECT ... INTO 变量`（PL/SQL 赋值）把变量名当成表名（实测把 `CNT` 当热表）；
  ② `FOR UPDATE` 被误认为 UPDATE 语句；③ `INSERT INTO /*+ hint */ TMP_X` 的真表名被 hint 挡住
  （实测漏掉 40 个 TMP 表）。
- **稀疏采集场景的误导性提示**：跨度 7 天但只有 654 秒有事件时，旧版会报"峰值是平均的 9884 倍"。
  现在先判断日志覆盖度，覆盖不足时改为提示"覆盖稀疏，均值参考意义有限"。

## V1.3 — 2026-09-19

**亮点：补上锁等待分析** —— 锁等待与长事务是两件事，此前只有后者。

### 新增

- **锁等待分析**（需 `SQL_TRACE_MASK` 含位号 29）：锁等待次数、累计等待、最长等待、
  等待时长五档分布、**最久等待 TopN**（等待方事务 ← 持有方事务、锁模式、表 ID、被等事务数）、
  **被争抢的表 TopN**（按累计等待）。
  采用现网真实格式 `trx[...] LOCK_TID (mode:X, table id:N) wait for N trxs, trx[...] used time:N(ms)`；
  `(us)` 单位统一折算成毫秒；判据为 `LOCK_TID` + `wait for` 双锚点，
  避免把 `LOCK_MONITOR`、`LOCK_R3` 之类**表名**误判成锁等待。
- **`DLCK used time:N(us)` 单独计数**：它是执行计划里锁操作符节点的**自身耗时**，不是等待时长，
  `0(us)` 是常态。单独列出以免与真锁等待混淆（否则等待数会被放大三个数量级）。
- **重复来源检测**：目录里同时存在散装日志与含同一批日志的压缩包时告警 —— 这种情况会让统计翻倍
  （实测 `D:\dmsql_log` 目录即如此）。只告警、不自动跳过，避免漏掉不同机器上的同名日志。
- 长事务口径改进：时间精度从秒提升到**毫秒**；把 `TRX: START` 纳入事务起点；
  新增"只见 START、未见结束"的事务计数（长期持锁/未提交的嫌疑对象）。

### 改进

- **性能**：未请求统计报告时跳过全部聚合（省掉全局锁与大 map）。
  同一 1GB 日志单文件解析由 2.27s 降到 **1.88s（549 MB/s）**。
- 帮助文本补充锁等待与长事务的说明与用法。

## V1.0 — 2026-09-18

**首个版本**。

- 单文件 Go 实现（纯标准库、零第三方依赖），编译即得单个静态二进制，不连库、不建表。
- 核心能力：把 `dmsql_*.log` 里带 `?` 的语句按日志中的 `PARAMS` 行**还原成真实参数值**，
  输出可直接复制到 disql 执行的 SQL。
- 基础筛选（时间、耗时、类型、用户、事务号、SQL 子串、条数）与基础统计。
- **与官方 DMLOG 工具的关键差异**（依据同一批现网日志实测）：
  参数还原成功率 **97.8% vs 官方 10.9%**；含逗号的参数值完整保留（官方会切掉前半截且仍标记"已替换"）；
  空值输出 `NULL`（官方输出空串会拼出非法的 `,,`）。
