# dmsqlq V2.7 使用说明 —— 达梦 SQL 日志解析工具

一句话：**把 `dmsql_*.log` 里带 `?` 的 SQL，按日志里的 `PARAMS` 行还原成真实参数值，输出可直接复制到 disql 执行的语句；另可出一份能直接看的性能统计报告。**

单个可执行文件 · 不连数据库 · 不建表 · 不装运行时 · 不联网 · GB 级日志秒级扫完。

> **本交付包内容**：3 个平台的可执行文件 + 本文档 + 发版更新记录 `CHANGELOG.md`，解压即用、可直接分享。
> 源码与设计文档不在包内，在项目目录 `DMSQLQ/` 下（`src/dmsqlq.go`、`设计与选型说明.md`）。
>
> | 平台 | 文件 | 用法 |
> |---|---|---|
> | Windows x64 | `dmsqlq.exe` | 双击或 `dmsqlq.exe --help` |
> | Linux x86_64 | `dmsqlq_linux_x64` | `chmod +x dmsqlq_linux_x64 && ./dmsqlq_linux_x64 --help` |
> | Linux arm64（鲲鹏/飞腾） | `dmsqlq_linux_arm64` | 同上 |

## 1. 三十秒上手

```bat
dmsqlq                          不带参数 → 显示用法，并直接告诉你「当前目录有什么、下一步敲什么」
dmsqlq .                        处理当前目录，输出全部可执行 SQL
dmsqlq . -m 1000                只要执行超过 1 秒的语句
dmsqlq . -s                     出统计报告（<日志名>_报告.html），生成后自动用浏览器打开
dmsqlq . -s -Q                  同上，但不要自动打开浏览器（批处理里连跑多份时用）
dmsqlq . -S                     只在终端扫一眼统计，不出文件
dmsqlq . -B 20 -o slow.sql      导出最慢 20 条的完整 SQL
```

> **不带参数时会先看一眼当前目录**：有日志就把「日志清单 + 可直接复制的下一步命令」列出来，
> 没有就给一条最朴素的例子 —— 完整的帮助（138 行）仍然照常打印在前面。
> Windows 下从资源管理器**双击 exe** 时，结束前会**等一次回车**，不会一闪而过。
> 想扫当前目录就写 `dmsqlq .`，多一个点而已。

## 2. 八个最常用场景

```bat
:: ① 先看全局：哪类语句最耗时间、哪张表最热、哪条最慢、有没有锁等待
dmsqlq /dmdata/log -s                        :: 出 HTML 报告（自动命名），屏幕只给要点
dmsqlq /dmdata/log -s -r 报告.md             :: 换个文件名/格式（Markdown 贴工单）
dmsqlq /dmdata/log -S                        :: 只要终端结论、不落文件（SSH 里快速判断）

:: ② 导出慢 SQL 去复现
dmsqlq /dmdata/log -m 2000 -o slow.sql       :: 超过 2 秒的全部语句
dmsqlq /dmdata/log -B 20 -N -o slow20.sql    :: 最慢的 20 条，纯 SQL

:: ③ 锁等待定位（阻塞排查，报告里给出"等待方事务号 + 表 ID + 锁模式"）
dmsqlq . -s                                  :: 报告里看"锁等待"一节：最久等待 TopN、被争抢的表 TopN
dmsqlq . -x 10133085467 -N                   :: 导出等待方事务当时在跑的 SQL（问题复现）

:: ④ 按表名 / 用户 / 时间段挑语句
dmsqlq . -l t_rim_invoice -n 50              :: 涉及某张表（-l = sql-like）
dmsqlq . -u COSMIC_SYS -m 1000               :: 某用户的慢语句
dmsqlq . -f "2026-09-09 23:52" -t "2026-09-09 23:55" -k SEL,UPD

:: ⑤ 复现某个事务（业务侧排查）
dmsqlq x.log -x 10130765548 -N               :: 该事务全部语句，按时间序
dmsqlq x.log -x 10130765548 -o trx.sql

:: ⑥ 压缩包直接喂 / 多目录 / 通配符
dmsqlq dm_log_20260910.tar.gz -B 10 -o slow.sql
dmsqlq D:/dmdbms/log D:/dmsql_log -s -o all.sql   :: 出报告，同时把 SQL 汇总到 all.sql
dmsqlq "dmsql_*.log" -m 500

:: ⑦ 排除干扰项，只看真正的业务负载
dmsqlq . -m 1000 -E CAL,ANALYZE,DBMS_STATS   :: 剔除调用与统计信息收集造成的"假慢"
dmsqlq . -s -E CAL                           :: 统计里也一并剔除（-E 同时作用于统计）

:: ⑧ 定期交付给开发商做 SQL 优化（Excel 交付件，详见 5.7）
dmsqlq . -e 交付.xlsx                        :: 出 Excel（清单默认 20 行）
dmsqlq . -s -e 交付.xlsx                     :: HTML 自己看 + Excel 发出去
dmsqlq . -e 交付.xlsx -p 500                 :: 清单要 500 行
```

## 3. 参数一览（每个都有短写和长写）

短名取首字母；同类用**大小写配对**方便记（`-m/-M`、`-k/-K`、`-s/-S`）。

```
筛选
  -f, --from TIME      起始时间；"2026-09-09" / "2026-09-09 23:52" / 完整时间均可
                       ⭐ 也可只给时刻（"09:00"）—— 表示「每天的 9 点起」，
                       用于「只看业务高峰、排除夜间跑批」，需与 -t 成对使用：
                         dmsqlq dmsql1001_all.tgz -f 09:00 -t 18:00 -s
  -t, --to   TIME      结束时间（同样支持纯时刻）
                       ⚠️ 注意：-f/-t 会同时决定**统计口径** —— 报告正文的
                       类型分布、最耗时模板、热表等只覆盖该时段（V2.5 起）
  -m, --min-ms N       只保留耗时 ≥ N 毫秒          -M, --max-ms N   只保留 ≤ N 毫秒
  -k, --op   LIST      只保留这些类型（默认 SEL,INS,UPD,DEL,DML,DDL,CAL,ERR）
  -E, --exclude-op LIST 排除指定语句。两种写法自动识别：
                        ① 事件类型码：CAL / DDL / SEL / INS / UPD / DEL …
                        ② 任意 SQL 子串（忽略大小写）：ANALYZE / DBMS_STATS / TMP_ …
                        例：-E CAL,ANALYZE,DBMS_STATS   剔除调用与统计信息收集
  -K, --all-ops        不做类型过滤（含 ORA 只解析、LGN 登录等全部）
  -u, --user NAME      只保留该用户
  -x, --trx ID         只保留该事务号（支持逗号分隔多个，如 -x 101,102）
  -O, --obj-map FILE   对象 ID → 表名 映射；DM 的 SQL 日志只记对象 ID，
                       给它一张映射表就能在锁等待里直接显示表名（见 5.6）
  -l, --sql-like STR   SQL 文本包含该子串（忽略大小写，按表名过滤很好用）
  -n, --limit N        最多输出 N 条

统计
  -s, --stats          生成统计报告（最高频用法）。默认落一份 HTML 到当前目录，
                       文件名取输入日志名 +「_报告.html」；屏幕只给简要要点（-q 可静音）。
                       内容：概览/类型分布(含耗时占比)/耗时分布(含分位数)/热表(含读写比)/
                       吞吐(QPS·TPS)/最慢语句/最耗时模板/用户与客户端/长事务(含利用率)/
                       锁等待/审计与恢复定位(危险操作·结构变更·LSN)/采集配置体检/判读提示。
                       不带 -o 时**不往 stdout 写 SQL**（可安心接管道）；想要 SQL 就加 -o。
  -S, --stats-only     只在命令行打简要统计：不出报告文件、也不导出 SQL ——
                       适合 SSH 里快速判断"这份日志有没有问题"。
  -r, --stats-out FILE 统计报告写入指定文件，按后缀选格式（配合 -s；单独给也行）：
                         .html/.htm → 单文件 HTML（带图表，浏览器打开即可，可打印为 PDF）
                         .md/.markdown → Markdown 表格（贴工单/文档）
                         .xlsx → Excel 交付件（多张工作表，给开发商做 SQL 优化用）
                         其他 → 纯文本（等宽对齐）
  -e, --excel FILE     Excel 交付件（.xlsx），定期交付给开发商做 SQL 优化用（详见 5.7）。
                       可与 -s 并用：一次扫描同时出「自己看的 HTML」+「发出去的 Excel」；
                       也可单独给，此时不生成 HTML、不弹浏览器。
                       -e auto 用输入日志名自动命名（<日志名>_交付.xlsx）。
                       行数 = -p（默认 20）；**调大 -p 即可导出完整清单**，报告仍只显示前 20 条。
                       不自动打开（它是发出去的文件）；屏幕只给简要结论，
                       **不会**把 SQL 写到 stdout —— 要 SQL 就再加 -o all.sql。
  -p, --top N          交付件（Excel）的行数，默认 20 —— 调大即可导出完整清单。
                       报告（HTML/Markdown/终端）各排行榜一律最多显示 20 条：
                       报告是给人看结论的，榜单/时段一长就没人读（-p 更小时按 -p 走）。
  -F, --full-sql FILE  完整 SQL 附件（跨节整批：含长事务/锁等待涉及事务的全部语句）。
                       本表同类的批量导出已由报告表头的「导出全部 TopN」按钮承担，
                       所以日常通常无需再翻附件。报告里单条语句可点击展开、
                       悬停预览、一键复制，无需再翻文件；附件的作用是整批导出，
                       方便一次拿去 disql 执行。含：最慢语句 TopN、最耗时模板 TopN，
                       以及长事务与锁等待涉及事务的全部语句（按事务号分组）。
                       默认与 -r 报告同名 +「.full.sql」；写 off 表示不生成。

输出
  -d, --danger         只输出审计命中的语句（高危操作 / 结构变更 / 大批量 DML），
                       用来单独导出"可能出事的语句"清单
  -o, --out FILE       输出到文件（默认 stdout）
  -B, --top-ms N       导出"最慢的 N 条"完整 SQL（按耗时降序）
  -T, --term S         语句结束符，默认 ";"；none 表示不加
  -N, --no-meta        不输出 -- 注释头（得到纯 SQL）
  -P, --no-params      不还原参数（输出仍是带 ? 的原始 SQL）
  -X, --skip-missing   只输出参数已还原成功的语句
  -C, --max-sql N      单条 SQL 超过 N 字符时截断（默认 0 不截断）

其他
  -A, --all-files      目录下所有 .log 都处理（不限 dmsql_ 前缀）
  -L, --loose          兼容 SVR_LOG=3 简单模式（此类日志没有会话块）
  -Y, --loose-key      参数关联放宽为 sess+stmt（忽略 thrd 线程漂移）
  -j, --jobs N         并发处理文件数（默认 CPU 核数）
  -q, --quiet          不打印进度与警告
  -h, --help           显示帮助                      -V, --version  显示版本

退出码：0 成功   1 未找到日志文件   2 参数或路径错误
```

> ⚠️ 与 V1.1 的差异：**`-s` 由"sql-like"改成了"stats"**（更符合首字母记忆），`--sql-like` 的短名改为 **`-l`**。
> 其余旧短名（`-f -t -m -k -u -x -n -j -o -q -V -h`）保持不变。

## 4. 输出长这样

每条语句之间**空一行**，方便肉眼分条、也方便整段复制后逐条执行：

```sql
-- 2026-09-10 09:43:18 · [INS] · 0ms · 1行 · SYSDBA · trxid:3816438 · DMSERVER_20260910_094318
insert into LOG_COMMIT values('2026-09-10 07:58:17.527','(EP[0] sess:...',NULL,...);

-- 2026-09-10 09:43:19 · [SEL] · 3ms · 1行 · COSMIC_FI · trxid:3816439 · KD1_20260909_235252
SELECT A.FId "id", A.fserial_no "serial_no" FROM t_rim_invoice A WHERE A.fbill_id = 'dac7228084004bd9b7c57e71e9f6f95c0';
```

注释头字段用 ` · ` 分隔（此前 `0ms 0rows` 挤在一起不好读）：

| 字段 | 说明 |
|---|---|
| 时间 | 该语句在日志里的时间戳 |
| `[类型]` | `SEL/INS/UPD/DEL/DML/DDL/CAL/ERR` |
| 耗时 | `0ms` / `3ms` / `1.4min`；`[ORA]` 等无耗时的事件不显示 |
| 行数 | `1行`（影响行数） |
| 用户 | 执行用户 |
| `trxid:` | 事务号（0 表示无活动事务，不显示） |
| 来源 | 日志短名（已去掉 `dmsql_` 前缀与 `.log/.gz/.zip` 后缀） |

- 加 `-N`（`--no-meta`）得到**纯 SQL**，只剩语句 + 空行；
- 多行 PL/SQL 块原样保留，**不追加多余结束符**（块尾已是 `end;`，可直接 `/` 执行）。

## 5. 统计报告：出文件还是只看一眼？

两个开关分工明确（**V1.9 起调整过语义，老用户请留意**）：

| 命令 | 报告文件 | 屏幕 | 自动开浏览器 | 说明 |
|---|---|---|---|---|
| `-s` | ✅ **自动生成** `<日志名>_报告.html` | 简要要点 + TOP5 | ✅ | **最高频用法**：出报告并直接打开 |
| `-s -Q` | ✅ 自动生成 | 简要要点 + TOP5 | ✗ | 批处理/连跑多份日志时用，只出文件不弹窗 |
| `-s -r 报告.md` | ✅ 写到指定名字/格式 | 简要要点 + TOP5 | 仅 HTML | 想换文件名或出 Markdown/纯文本 |
| `-s -o all.sql` | ✅ 自动生成 | 简要要点 + TOP5 | ✅ | 报告 + SQL 一起要，SQL 进 `all.sql` |
| `-S` | ✗ 不生成 | 完整统计文本 | — | 只要"在终端扫一眼"，SSH 里快速判断。**不能与 `-r` 同用** |
| `-r 报告.md`（单独用） | ✅ 写 | 只提示一行"已写出" | 仅 HTML | 视为"要文件不要刷屏" |

**报告会自动打开**（V2.0 起）：报告一落盘就顺手用系统默认程序打开，不必再去目录里找那个文件。
Windows 用 `explorer.exe`，macOS 用 `open`，Linux 优先 `xdg-open`。
打不开**不算失败** —— 只是不弹窗，报告文件一定在（会提示"手动打开即可"），
无桌面环境（SSH / 没有图形界面）下静默跳过、不往终端吐噪音。

> 为什么 Windows 不用常见的 `rundll32 url.dll,FileProtocolHandler`：它是公认的 LOLBin
> （可被用来执行任意代码），**不少企业 EDR 会直接拦掉**（本机开发沙箱就把它拦了），
> 所以改用 `explorer.exe`，`rundll32` 只作为降级备选。

**为什么 `-s` 直接等于"出报告"**：报告做好之后 `-s` 会变成使用频率最高的命令，
而指定它的人核心目标几乎必然是"我要看报告"。既然意图已经明确，就不该再逼他多打一个
`-S` 才能同时把文件落下来。于是 **`-s` = 出报告**，轻量的"只想扫一眼"交给 `-S`。

**为什么 `-s` 不再往屏幕刷 SQL**：老版本 `-s` 会把几十万条 SQL 一股脑打到 stdout，
屏幕滚几百 MB，既把统计结论冲散，也**没法接管道**（`| grep`、`| head` 全废）。
现在分工是：

- **stdout** 只放 SQL（所以 `dmsqlq x.log | grep ...` 永远干净）；
- **stderr** 放统计要点、报告路径、进度提示；
- 不带 `-o` 时 `-s` **完全不往 stdout 写 SQL**；真想要 SQL 就显式 `-o 文件名`。

**不带任何参数**仍是「显示帮助」（138 行用法），不跑解析、不刷统计；
区别是现在会**额外看一眼当前目录**，把日志清单和下一步命令列出来（见第 1 节）。

报告十五节及判读（`-p N` 控制各排行榜条数）：

| 节 | 看什么 | 判读要点 |
|---|---|---|
| 概览 | 文件/记录/SQL 事件/命中语句/参数还原率/日志跨度/吞吐 | 还原率 <95% 通常是日志缺 `PARAMS` 行（掩码 28 未开） |
| **语句类型分布** | 各类型次数、次数占比、累计耗时、**耗时占比 + 条形图** | 次数多≠问题大：次数占比与耗时占比**偏离大**才说明"次数不多但很慢"或"数量大但很轻" |
| 执行耗时分布 | `<1ms … ≥60s` 七档 + 条形图 | 有 ≥60s 的桶就优先排查 |
| **吞吐与时轴** | 平均/峰值 QPS、平均/峰值 TPS、回滚率、有事件的秒数、**最长静默空档** | 峰值≫平均说明负载是尖峰型；静默空档可能是业务停顿或**采集中断** |
| **负载时间分布** | **高峰时段 TopN**（时段/SQL 数/平均 QPS/累计耗时/COMMIT/ROLLBACK/占比 + 条形图）；HTML 与 Markdown 里另有完整时间轴 | **看业务高峰就看这节**；粒度按跨度自适应（分钟/小时/天）。空时段说明该时段无事件 = 业务低峰或采集中断 |
| **热表 TopN** | 表名、语句数、读写次数、累计耗时、最大、耗时占比 + 条形图 | 直接回答"该优化哪张表"；占比高的表下一步用 `-l 表名` 单独抽 |
| 最慢语句 TopN | 单条最慢（耗时/行数/类型/用户/时间/EXEC_ID/SQL） | SQL 列可**悬停预览 / 点击展开全文 / 一键复制**，表头**一键导出全部 TopN**（见 5.3） |
| 最耗时语句模板 TopN | 同模板（字面量/数字已归一化）的累计耗时/次数/平均/最大 + 样例语句 | **优化收益最大**的地方；样例同样可展开/复制，表头可**一键导出全部模板样例** |
| 用户排行 | 各用户语句数、累计、最大 | 定位哪个业务账号在压库 |
| **客户端排行** | `appname @ IP` 的语句数、累计、最大 | 定位是哪个应用/主机在压库（生产日志 appname 常为空，此时看 IP） |
| 长事务 TopN | trxid、用户、跨度、**SQL 执行耗时**、**利用率**、语句数、起止（需掩码 29 的 trxid） | **单条 SQL 快 ≠ 事务没问题**；长事务拖 undo 与锁。**利用率 = 事务内 SQL 累计耗时 ÷（跨度 + 首条 SQL 耗时）**，利用率低 = 占着事务不干活（长时间持锁、忘了提交），比"SQL 慢"更该先处理 |
| **锁等待（掩码 29）** | 锁等待次数/累计/最长、等待时长分布、**等待最密的一秒**、**最久等待 TopN**（等待方 trxid+用户 ← **持有方 trxid+用户**、锁模式、对象、被等事务数、**溯源命令**）、**被争抢的表 TopN**（次数/累计/最长/锁模式/等待方用户/最长发生时间） | **真正的阻塞证据**，与长事务不是一回事（见 5.2）；持有方信息回答"谁在持锁"；对象只有 ID 时见 5.6 |
| **审计与恢复定位** | 危险操作时间倒序（DROP / TRUNCATE / 无 WHERE 的 DELETE·UPDATE / 权限变更 / 大批量 DML）：时间、对象、**用户 + 客户端 + 线程**、影响行数、**最近提交 LSN**、状态（已执行 / **仅解析未执行**）；被反复操作的对象；**结构变更时间线**（CREATE/ALTER/RENAME + 类型统计） | **误删/误改的事件记录与恢复定位**。`[ORA]` 行在这里终于有用：语句到达服务器却没执行成功（权限不足/超时/取消/回滚）也会留证；LSN 是不完全恢复的锚点。见 5.5 |
| **采集配置体检** | 据日志实际内容反推 `sqllog.ini`：时间戳精度、耗时覆盖（掩码 24/25）、PARAMS（28）、事务与锁（29）、`[ORA]`（27）、`[LGN]`（31）、`[ERR]`（23）、EXECTIME 单位 | **"分析不出锁等待 / 没有参数"的第一嫌疑是采集配置，不是解析器** —— 这一节把结论和改法直接写出来，不用自己去对掩码 |
| 判读提示 | 自动给出的可操作建议（含可直接复制的下一条命令） | 直接抄里面的命令 |

> **统计口径（两个方向要分清）**
> - `-f/-t/-m/-M/-k/-u/-x/-l/-n` 只影响**输出哪些 SQL**，统计**仍反映日志全貌**（报告会列出当前筛选条件），所以"先看统计、再筛语句"是正确顺序；
> - **`-E` 的排除会同时把该批语句剔出统计** —— 因为它表达的是"这类语句不是有效负载"（典型是统计信息收集、调用类）。
>   被排除的条数会在概览里单列一行 `已排除`，便于核对。

| **HTML** | `-r 报告.html` | 自己判读、发给同事、投屏讲、归档；浏览器直接打开，Ctrl+P 可出 PDF | ✅ 条形图 + KPI 卡片 |

### 5.2 长事务 ≠ 锁等待（最容易混的两个概念）

二者**不是一回事**，数据来源、判定依据、优化方向都不同：

| | 长事务 | 锁等待 |
|---|---|---|
| 是什么 | 一个事务从开始到结束**持续很久** | 某个会话在**等另一个会话释放锁** |
| 判定依据 | 同一 `trxid` 的起止时间跨度 | 日志里 `trx[...] LOCK_TID (mode:X, table id:NNN) wait for N trxs, trx[...] used time:N(ms)` 这类行 |
| 单位/精度 | 秒~分钟级（跨多条语句） | 毫秒级（单次阻塞） |
| 危害 | 占 undo、放大日志、撑大回滚段 | 业务直接卡住/超时 |
| 典型成因 | 大批量 DML 未分批提交、应用忘了 commit | 热点行更新、缺索引导致锁范围扩大、长事务持锁 |
| 优化方向 | 拆小批次、及时提交 | 缩短持锁时间、改 SQL/加索引、调整并发 |

**两者又有因果关系**：长事务往往正是锁等待的制造者。
所以报告里同时给出"最久等待的持有方 trxid"和"长事务清单"，可以直接对上：**谁持锁最久 → 它就是长事务**。

还有一类**最容易误读**的行：`DLCK used time:0(us)`。
它是**执行计划里锁操作符（DLCK 节点）的自身耗时**，不是等待时长；`used time:0(us)` 是常态，
**看到它不代表发生了锁等待**。本工具把 DLCK 单独计数，不与锁等待混在一起。

> 用法示例：`dmsqlq . -s`（报告里看锁等待全貌） → 拿到"等待方 trxid" → `dmsqlq . -x <trxid> -N` 看它当时在跑什么 SQL →
> 拿到"表 ID"去数据字典反查表名（见第 7 节注意事项）。

### 5.3 报告里 SQL 怎么看全、怎么复制、怎么整批拿走？（HTML 报告直接搞定）

从 **V1.8** 起，HTML 报告里的语句列本身就是交互组件，**不需要再开另一个文件对着序号找**：

| 操作 | 效果 |
|---|---|
| 平时 | 只显示摘要，太长自动省略号 —— 排版清爽 |
| **鼠标悬停** | 浮出预览完整语句（超 20 行时给前 20 行 + "共 N 行 M 字符"提示） |
| **点击摘要** | 行内展开 / 收起全文（深色代码块，可滚动，长 SQL 不撑破表格） |
| **`[复制]`** | 完整语句（**参数已还原**）直接进剪贴板，粘进 disql 就能跑 |
| **Esc 键** | 收起全部已展开的语句（展开很多条时不必逐条点回去） |

从 **V1.9** 起，每张表**上方多一个「导出全部 TopN」按钮** —— 想拿走的不是某一条，
而是"这一整类"，点一下就下载成一个 `.sql` 文件：

| 按钮 | 下载文件 | 内容 |
|---|---|---|
| 最慢语句表上方 | `slow_top10.sql` | 最慢 TopN 全部语句 |
| 最耗时模板表上方 | `template_top10.sql` | 每个模板的代表语句 |
| 高危操作表上方 | `danger_top4.sql` | 审计命中的危险操作 |

导出的文件长这样 —— **每条前面一行注释头说明它是谁，语句压成单行不折行**：

```sql
-- [#1] 58.37s  00:01:28  用户 COSMIC_FI  行数 100
SELECT A.fcostaccountid "costaccount", ... WHERE ...;

-- [#2] 50.16s  00:01:06  用户 COSMIC_SYS  行数 500
DELETE FROM t_isc_sf_proc_log WHERE ...;
```

- `--` 是 SQL 行注释，所以**整个文件仍是合法 SQL**，可以直接丢给 disql 跑；
- 注释头里的 `#n` 与表格里的序号一一对应，跑出错了好回头查；
- 单行不折行，粘进工单、丢进 `grep`、给同事看都不会散架。

生效位置：**最慢语句 TopN**、**最耗时语句模板 TopN**、**审计明细**三处。
报告仍是**单文件、零依赖、双击就开**，直接发给别人也不会丢交互。

#### 5.3.1 长表默认折叠（V2.7 起）

报告里的榜单动辄 20~48 行（锁等待尤其长），一屏刷不完，**真正要看的那几条反而被淹**。
V2.7 起，**超过 8 行的表格默认只显示前 8 行**，下方多一个「展开全部 N 行」按钮：

| 操作 | 效果 |
|---|---|
| 默认打开 | 只显示前 8 行 —— 一屏读完「最该看的头几名」 |
| **点击「展开全部 N 行」** | 就地展开其余全部行，按钮变成「收起」，再点收回去 |
| **打印 / 导出 PDF** | **自动全部展开**（按钮本身也不打印）—— 归档件、留档、发给别人都是完整的 |

生效位置：热表、最慢语句、最耗时语句模板、长事务、锁等待（最久等待）、高危操作、结构变更。

> **为什么是 8 行**：20 行的榜单折完剩 8 行，正好一屏看完头几名；
> 再少就开始丢有效信息（第 9、10 名常常仍有优化价值）。
> 折叠只影响"屏读时的观感"，**不影响任何统计数字，也不影响打印与 PDF**。
>
> 需要**完整清单一次拿走**的（比如给开发商改），仍走表上方的「导出全部 N 条 SQL」，
> 与折叠互不影响 —— 那个按钮导的始终是全量。

**那 `.full.sql` 附件还要不要？要，但角色变了 —— 从"拿全文的唯一途径"变成"跨节整批导出"。**

| 文件 / 按钮 | 作用 |
|---|---|
| `报告.html` | 看结论 + **看全文 + 复制任意一条**（V1.8 起） |
| 表头「导出全部 TopN」 | **本表同类**一次拿走，点一下就有（V1.9 起） |
| `报告.html.full.sql` | **跨节整批**：含长事务与锁等待涉及事务的全部语句，按事务号分组 |

> 一句话分工：**要"这一类"用表头按钮，要"这一个事务/这一批"用 `.full.sql` 附件。**

- 生成规则：用了 `-r` 就自动产出同名 `.full.sql`；`-F off` 关闭；`-F 别的名字` 自定义。
- 附件内容：最慢语句 TopN、最耗时模板 TopN、**长事务与锁等待涉及事务的全部语句**
  （按事务号分组，参数已还原，可直接执行）。
- 只想要某一个事务的语句，也可以单独抽：
  `dmsqlq <同一路径> -x 10131019540 -N -o trx.sql`（`-x` 支持逗号分隔多个事务号）。

**体积红线 2 MB**：内嵌全文必然撑大文件，审计命中在大日志上可达上万条。
所以设了总预算 —— 在预算内正常内嵌；**超出后该行自动退回"摘要 + 悬停预览"**，
并标注「全文见配套 .full.sql 附件」。实测 1 GB 现网日志的报告约 **533 KB**，远在红线内。

> 纯文本（`-o x.txt`）与 Markdown（`-r x.md`）**无法内嵌交互**，那里仍然只有摘要、
> 全文看附件。想要点击展开/复制，请出 HTML：`-r 报告.html`。

> 报告里若看到 **`[参数未还原]`** 标记，表示该语句在日志里**前面就没有 `PARAMS` 行**（采集侧缺），
> 不是解析失败 —— 这不是工具能补的，查 `sqllog.ini` 的 `SQL_TRACE_MASK` 是否含 **28**。


### 5.4 耗时单位：`(ms)` 还是 `(us)`？

`EXECTIME` 的单位由库参数 **`EXECTIME_PREC_FLAG`** 决定（`0`→毫秒、`1`→微秒）。
本工具**读日志里的单位标记并统一换算成毫秒**，所以：

- 微秒制的库不会出现"整体差 1000 倍"的读数错误；
- 两份来自不同单位库的报告**可以横向比较**；
- 报告「采集配置体检」一节会明示这份日志用的是哪种单位（实测本机现网日志全是 `ms`）。

> 顺手区分一个容易混的：`DLCK used time:0(us)` 的微秒是**执行计划节点的自身单位**，
> 与 `EXECTIME_PREC_FLAG` 无关，也不代表"发生了锁等待"（详见 5.2）。

### 5.5 误删了怎么定位？审计与恢复定位怎么用

报告里的「审计与恢复定位」一节就是为这件事准备的。它把 SQL 日志里所有**可能出事**的操作
按时间倒序列出来，每条给全四要素：

| 要素 | 从哪来 | 用途 |
|---|---|---|
| 时间点 | 行首时间戳（带日期） | 定位到分钟；配合备份/归档确定恢复目标点 |
| 对象 | 从 SQL 文本提取的表名 | 明确影响面 |
| 操作人 | `user:` + `appname@ip` + **`thrd:` 线程号** | 线程号能区分"同一秒里两个连接做了同样的事"（实测现网真有这种并发重复执行） |
| 影响行数 | `ROWCOUNT:` | 判断是误删一行还是整表 |
| **提交 LSN** | `TRX: COMMIT LSN[…]`（按 30 秒采样） | **不完全恢复的锚点**，交给 DBA 用归档日志恢复 |

识别范围：`DROP TABLE/INDEX/VIEW/USER/SCHEMA…`、`TRUNCATE`、**无 WHERE 的 DELETE / UPDATE**、
`GRANT`/`REVOKE`、`CREATE|ALTER|DROP USER`、`ALTER … DROP COLUMN/PARTITION`、
以及**大批量 DML**（DELETE ≥1 万行 / UPDATE ≥5 万行）。

三个容易被忽略但很实用的点：

1. **`[ORA]` 行参与审计**。它是"语句到达服务器并完成语法解析"，但不一定执行成功
   （权限不足、超时、客户端取消、事务被回滚）。这类记录标为 **「仅解析未执行」**——
   "有人试图删这张表"本身就是证据。工具会按语句句柄把 `[ORA]` 和执行行配对：
   配上就是完整链路（带影响行数），配不上就保留为"仅解析"。
2. **审计不受输出筛选影响**。和统计一样在筛选之前采集，所以 `-m 1000`、`-k SEL`、`-n 100`
   都不会让一条 `DROP TABLE` 从审计清单里消失。
3. **只要审计命中的语句**：`dmsqlq <日志> -d -N -o danger.sql` —— 单独归档或复核。
   完整语句（含参数还原）在配套附件的「4) 审计明细」。

> 一条边界要说清：本工具给的是**定位**（时间/对象/操作人/LSN），不是恢复手段本身。
> 能不能恢复取决于你的备份策略、归档是否齐全、回收站是否还在 —— 具体命令请按 DM 版本
> 与手册确认后再执行。

### 5.6 锁等待里只有对象 ID，怎么拿到表名？

DM 的 SQL 日志只记对象 ID（`table id:10175`），不记表名 —— 这是日志本身的限制。两条路：

**① 一次性反查（推荐）**：报告里会自动给出可直接复制执行的 SQL：

```sql
SELECT ID, NAME, SCHID FROM SYS.SYSOBJECTS WHERE ID IN (8130, 10175, 1060493);
```

把结果存成 UTF-8 文本（每行 `ID=表名`，或直接把 ID 与表名两列粘进去），下次带上它：

```bat
dmsqlq /dmdata/log -s -O 对象映射.txt
```

报告里的"对象ID 10175"就变成"**T_ISC_JOB_INST (ID 10175)**"，仍然保留 ID 便于对照。

**② 直接查数据字典**（各版本视图列名略有差异，可试这些）：

```sql
SELECT * FROM DBA_OBJECTS  WHERE OBJECT_ID = 10175;   -- 通用
SELECT * FROM SYS.SYSOBJECTS WHERE ID = 10175;        -- 达梦自有
```

### 5.7 Excel 交付件：定期交付给开发商做 SQL 优化

**场景**：系统上线后，每隔一段时间（每周/每月）把这份日志的慢 SQL 清单交给开发商，
让开发商据此优化。HTML 报告不适合这个用途 —— 它漂亮但不好"改"，对方要的是能排序、能批注的表。

```bat
dmsqlq D:/dmsql_log -s -e 交付_202609.xlsx     :: HTML 自己看 + Excel 发出去
dmsqlq D:/dmsql_log -e 交付_202609.xlsx -p 500 :: 只要 Excel，清单要 500 行
dmsqlq . -e auto                               :: 自动命名 <日志名>_交付.xlsx
```

打开后十张工作表，**第一张是背景，第二张是行动项**：

| 工作表 | 给谁看 | 内容 |
|---|---|---|
| **概览** | 双方 | 分析范围、关键指标、耗时分布、采集配置体检、**口径与说明**、判读提示 |
| **SQL优化清单** ★ | 开发商 | 语句模板按**累计耗时降序**：执行次数 / 平均 / 最大 / 占总耗时 / **优先级** / 样例 SQL |
| **慢SQL明细** | 开发商 | 最慢 N 条逐条列全（时间、耗时、类型、行数、用户、EXEC_ID、来源日志、完整 SQL） |
| **热表** | 开发商 | 表名、读写次数、读写比、累计耗时、耗时占比 → 索引设计的依据 |
| **语句类型分布** | 双方 | 各类型的次数占比 vs 耗时占比（找出"次数不多但很慢"的那类） |
| **锁等待** | 双方 | 指标 + 等待时长分布 + 最久等待明细（等待方/持有方）+ 被争抢的表 |
| **长事务** | 双方 | 跨度、SQL 执行耗时、利用率、语句数 + 每事务语句数分布 |
| **时段分布** | 双方 | 按分钟/小时/天的时间桶：SQL 数、QPS、耗时、COMMIT/ROLLBACK |
| **用户与客户端** | 双方 | 定位"是哪个应用在压库" |
| **结构变更与高危操作** | 双方 | 最慢语句涉及对象的最近一次 DDL、高危操作、结构变更时间线 |

三点使用提示：

1. **「SQL优化清单」的优先级是透明可查的**：该模板累计耗时 ÷ 本次语句总耗时，
   ≥10% 记「优先」、3%~10% 记「次之」、其余「一般」。规则写在表底说明行里，
   对方能看到这个判断怎么来的。**从第一行往下改，收益最大。**
2. **里面是"真数字"**：所有数值单元格是数值而非文本，可以直接排序、求和、拉透视表、
   写条件格式 —— 对方想按「平均耗时」再排一次，或只筛「次数 > 100 且最大 > 1s」，
   都不用先做分列转换。
3. **行数用 `-p` 控制**：默认 **20** 行；`-p 200` 就出 200 行的**完整清单**（报告那边不会跟着变大 ——
   报告各榜一律最多 20 条）。
   另外 `-e` 会顺带生成同名 `.full.sql`，里面是 TopN 语句与相关事务的完整 SQL，可直接整批执行。

> 交付件**不会**自动打开（它是发出去的文件，不是要立刻看的报告），路径会打印在屏幕上。
> 屏幕只给简要结论，**不会**把 SQL 刷到 stdout；确实想连 SQL 一起导就再加 `-o all.sql`。

### 5.8 没有锁等待日志，怎么看出「卡在锁上」？看错误码分布

现场常见一种情况：采集侧没开掩码 29（日志里没有锁等待明细），于是一堆问题只剩"慢"这个线索。
其实**错误码分布**这时很有用 —— 报告里新增的「错误码分布」小节按错误码列出**次数 / 占比 / 累计耗时 / 平均**：

```
  错误码分布（[ERR] 行，共 4,581 条）
  错误码              次数      占比      累计耗时        平均
  -608              4,509     98.4%        79.6h       1.1min
  -6007                69      1.5%       8.6min        7.44s
  -6602                 3      0.1%       51.74s       17.25s
```

一眼就能看出问题：**`-608` 只占 98% 的次数，却吃掉 79.6 小时**（同期日志跨度只有 1.36 小时）——
每条都要等满超时阈值（平均 63.5 秒）。**只看次数会以为"这不是主要问题"，看耗时才知道它是头号问题。**

> ⚠️ **`-608` 的正确读法**：它是「**会话请求超时 / 锁超时**」。按达梦官方社区的口径，
> 它本身**只说明超时，不能单凭这一行断定就是锁等待** —— 应用侧 `setQueryTimeout`、
> 语句本身太慢、网络/驱动超时都可能给出这个码。
> **要定性**，得在库上核对 `V$TRXWAIT`（谁在等谁）/ `V$LOCK`，或让采集侧把
> `SQL_TRACE_MASK` 补上 **29**，让日志直接记录锁等待，再用本工具的「锁等待」一节复核。
> 本工具不会替你下这个结论，只把"该去看哪"指出来。

其余错误码含义请以达梦官方文档为准。

## 7. 注意事项（使用者必读）

1. **编码**：全程按字节处理、不解码 —— **GBK 日志输出还是 GBK，不会乱码**。要 UTF-8 先 `iconv -f GB18030 -t UTF-8`。
2. **耗时单位**：**自动识别并统一换算成毫秒**。`EXECTIME` 的单位由 `EXECTIME_PREC_FLAG` 决定
   （`0`→毫秒、`1`→微秒），日志里的 `(ms)` / `(us)` 标记就是依据 —— 所以微秒制的库不会差 1000 倍，
   不同单位库的报告也能横向比较。报告「采集配置体检」一节会写明本次用的是哪种单位。
   （锁等待的 `used time:N(ms|us)` 自带单位，**不受** `EXECTIME_PREC_FLAG` 影响，同样折算成毫秒。）
   想核对配置可以查：
   ```sql
   SELECT MODE_NAME,PARA_NAME,PARA_VALUE FROM V$DM_SQLLOG_CONFIG
    WHERE PARA_NAME IN ('SQL_TRACE_MASK','EXECTIME_PREC_FLAG');
   ```
3. **日志里没有的东西还原不出来**（采集配置问题，不是解析问题）：

   | 缺什么 | `SQL_TRACE_MASK` 位号没开 |
   |---|---|
   | `PARAMS(SEQNO...)` 参数行 | 28 |
   | `EXECTIME:` / `ROWCOUNT:` | 24、25 |
   | **锁等待、`TRX: START/COMMIT`** | **29** |
   | `[ORA]` 原始语句 / `[LGN]` 登录 / `[ERR]` 报错 | 27 / 31 / 23 |

4. **目录里别同时放散装日志和打包了同一批日志的压缩包**：会把统计翻倍（工具检测到同名日志会告警，
   但不会自动跳过 —— 不同机器上同名日志是合法情况，自动跳过会丢数据）。建议一次只传一种。
5. **表 ID 反查表名**：锁等待报告给的是 `table id:10175` 这类**对象 ID**。报告里会自动生成一条
   可直接执行的反查 SQL（`SYS.SYSOBJECTS`），把结果存成文本再加 `-O 文件名` 重跑就能直接显示表名 ——
   详见 5.6。也可以自己用 `DBA_TABLES` / `V$LOCK` 对时间点核对（不同 DM 版本视图列名略有差异）。
6. `SVR_LOG=3`（简单模式）的日志没有会话块，工具会提示，加 `-L` 可解析。
7. `-B`（top-ms）会关掉多文件并发，以保证"全局最慢"的准确。
8. **吞吐参考**：单线程处理热数据（刚读过、在系统缓存里）约 500 MB/s；**冷盘首读受磁盘限制，约 150 MB/s**，
   这时 `-j 4` 最快、`-j 8` 已无收益（同一块盘的读带宽见顶）。
9. **长事务统计的口径与上限**：按同一 `trxid` 的首次事件 → 末次事件计算跨度（起点若是 `TRX: START` 更准）。
   识别到 50 万个事务后不再扩大统计表（防超大日志吃内存），此时报告会提示"只覆盖先出现的部分"，
   建议按文件或时间段分批扫描。
10. **记录边界**：判定"新记录"的判据是 **合法时间戳（3 位毫秒或 6 位微秒）+ 紧跟 `" (EP["`**，
    这挡住了"参数值里带换行的伪时间戳续行"（如 `2026-09-09 23:54:15:015#1200`，第 20 位是 `:`）。
    实测本机现网 26,799,837 条合法时间戳行里"后随不是 ` (EP[`"的有 **0 条**。
    老版本 DM 日志（无 `EP[n]` 段）与 `SVR_LOG=3` 简单模式会自动切回宽松判据，仍能正常解析。
    唯一残留的歧义是：**没有 ` (EP[` 的老格式日志**里，续行恰好写成长得一模一样的时间戳 —— 这种日志现实中未见过。

## 10. 还能加什么诊断维度（按价值排序）

工具当前已实现"能从 SQL 日志可靠拿到"的部分。下面这些是**可以再加**的方向，按"判读价值 ÷ 实现风险"排序，
其中需要现场样本的已标注 —— 先说清楚**哪些不能做**：DM 的 `dmsql_*.log` 里**没有执行计划、没有逻辑读/物理读、
没有 buffer hit**（不在 SQL_TRACE_MASK 的可选项里），所以"是否走索引""扫描了多少块"这类结论**无法从 SQL 日志得出**，
只能靠 SQL 文本 + 行数 + 耗时来间接推断。

| # | 诊断维度 | 价值 | 需要什么 | 状态 |
|---|---|---|---|---|
| 1 | **单条慢 SQL 的时间聚集**（某模板的耗时按小时/分钟分布） | 高：一眼看出是"定时任务窗口"还是"全天都慢" | 已有数据，纯计算 | 待加 |
| 2 | **每事务语句数分布**（逐条提交 vs 批量提交） | 高：逐条提交是批量导入慢的头号原因 | 已有 trxid | 待加 |
| 3 | **读/写放大比**（按表统计读次数 ÷ 写次数） | 中高：读多写少却慢的表通常缺索引 | 已有热表数据 | 待加 |
| 4 | **两次报告对比（环比）** | 高：同一 SQL 昨天 10ms 今天 2s，比绝对值更有信息量 | 两份报告的 diff 逻辑 | 待加 |
| 5 | **会话粒度画像**（单会话语句数/总耗时/最长空闲） | 中高：识别连接池配置不当（长空闲、单连接串行压库） | 已有 sess 句柄，需增加内存表 | 待加 |
| 6 | **DDL 变更时间线**（谁在何时改了哪张表） | 中高：性能劣化常紧跟一次 DDL | 已有 DDL 事件 | 待加 |
| 7 | ~~**错误码归类**~~ ✅ **V1.6 已做** | 高（若采集开了） | 已从 `[ERR(-2111)]` 里抽错误码并给出分布（本机现网实测有 30 行 `[ERR]`，主要错误码 `-2106`） | 已完成 |
| 8 | **非锁等待类等待**（IO、日志刷盘、网络） | 高 | 需要确认 DM 是否记录、以及长什么样 → **请提供样本** | 需调研 |
| 9 | **死锁检测** | 高（若发生） | 死锁信息在 `dm_*.log` 或 `[ERR]` 里，需样本 | 需调研 |
| 10 | **采集完整性自检**（每小时应有秒数 vs 实际有事件秒数） | 中：防"数据缺失导致的误判" | 已有秒桶数据，扩展成按小时 | 待加 |

> 需要你配合的只有三件：**提供 `[ERR]` 行样本、确认是否有非锁等待类等待行、提供一份死锁现场日志**。
> 有样本就能把 7/8/9 做掉；1~6、10 是我这边纯计算，随时可以加。

并用 ⚠️ 标出会影响判读结果或使用习惯的变化。

当前版本 **V2.7** 要点（主题：长列表折叠 + QPS 卡片自带口径说明）：

- **长表默认折叠**：超过 8 行的表格默认只显示前 8 行，下方给「展开全部 N 行」按钮，
  点一下就地展开、再点收起。覆盖热表 / 最慢语句 / 最耗时模板 / 长事务 / 锁等待 / 高危操作 / 结构变更

- **QPS 被低估时 KPI 区自带口径说明**：峰值 QPS「33」与峰值 TPS「4,933」并排时，
  卡片下方会多一条醒目提示，写明「这两个 QPS 是日志记到的语句数、不是业务真实吞吐、
  不要与 TPS 横向比较」。实测两者差 150 倍，根因是日志里 2,158 万条 COMMIT
  只配 5.3 万条 SQL 语句行
  > 口径放在卡片**下方**而非卡片里：卡片窄、会被省略号截成「33（日志…」**等于没说**；
  > 该提示只在 QPS 真被低估时出现，不占正常报告的版面
- 本版为**纯展示层改动，不动任何统计数字**：回归基线 2,402,022 / 134,395 / 98.60% 与 V2.6 一致

更早的 V2.6 要点（修正误报的信号 + 模板加「最快」列 + QPS 低估告警）：

- 🩸 **修正「SELECT * 取全字段」误报**：DM 常见的双层分页写法
  `SELECT * FROM (SELECT TOP 0,11000 <明确列> FROM ...) WHERE ROWNUM <= 11000`
  里，星号只在**外层包装**上，内层列是明确写出来的。旧判据把它全判成了取全字段。
  现在先剥包装再诊断，`SELECT *` 只在直接查基表时才报
- **「最耗时语句模板」新增「最快」列**（HTML / Markdown / 终端 / Excel 都有）。
  **最快 / 平均 / 最大 一起看才能定优化方向**：三者接近 = 稳定慢（缺索引/写法，改了就好）；
  最快远小于平均 = 时快时慢（计划突变、数据倾斜、偶发锁等待），先查为什么不稳定
- **新增三个据语句形态就能确证的信号**（不是猜的）：
  · `运行时建索引`（`EXECUTE IMMEDIATE 'CREATE INDEX ...'` 这类脚本，实测有模板跑了 17,613 次）
  · `超长 IN 列表`（≥100 个字面量，实测有模板拼了 999 个值、单条 SQL 49 KB）
  · `单次取数过大`（≥5000 行，实测有模板每次取 11,000 行）
  · 以及 `快慢差异极大`（最快与平均差一个数量级以上 → 明确提示"不是单纯缺索引"）
- 🩸 **QPS 被低估时会显式告警**：本批日志若"事务事件数 ≫ SQL 语句数"，
  说明 SQL 语句在日志里没记全，**QPS 只是"日志里记到的语句数"，不能与 TPS 横向比**。
  实测某份日志单文件里 COMMIT 行是 SQL 执行行的 80 多倍（单个句柄就对应 5.3 万条 PARAMS 行）
- **排序依据写进报告正文**：按影响占比（= 次数 × 平均耗时）排。
  最理想的判据本是**逻辑读**，但达梦的 SQL 日志不记录逻辑读，只能退而用累计耗时作代理
- V2.6 只改判读口径与文案，**计数/耗时/还原率与 V2.5 完全一致**（2,402,022 / 134,395 / 98.60%）

更早的 V2.5 要点（压缩包提速 1.58×、时间段作用到统计、优先优化推荐）：

- **⭐ 超大压缩包快 1.6 倍，而且看得见进度**：5.44 GB tar.gz（解压后 107 GB）
  **338 s → 214 s**。主要来自两处：① gzip 少了一层 4 MB 读缓冲，flate 每次只向
  底层要 512 字节，107 GB 触发约 2 亿次系统调用（补上后解压 161.7 s → 60.2 s）；
  ② 现网日志 98.4% 的行是 `PARAMS` 行（执行行只占 0.012%），原来每条都完整解析，
  改为**延迟解析**（真正命中才解）。处理过程中显示进度、速度、剩余时间，不再黑屏干等
- ⚠️ **`-f` / `-t` 现在同时决定统计口径** —— 这是本版最重要的语义变化。
  只想看业务高峰时：`dmsqlq dmsql1001_all.tgz -f 09:00 -t 18:00 -s`，
  夜间跑批不再污染排名（实测命中语句 2,116→159，类型分布同步收窄，P99 29.86s→1.32s）。
  报告头部会把「统计时间窗口」标出来，并注明窗口外排除了多少条。
  **其余筛选（`-k/-m/-u/-x/-l`）行为不变**，仍只筛输出
- **纯时刻写法**：`-f 09:00 -t 18:00` = 「每天的这个时段」，跨多天日志不必逐个打日期
- **⭐ 报告新增「优先优化推荐」**（HTML / 终端 / Markdown 都有）——
  按**影响占比**（该语句累计耗时 ÷ 全部语句耗时）排序，直接给「先改哪条、为什么、怎么改」：
  除占比外还给**问题信号**（`SELECT * 取全字段` / `无 WHERE 疑似全表扫描` /
  `前导通配 LIKE` / `高频轻量` / `偶发极慢` / `单次即慢` 等）与**建议动作**。

<summary>V1.9 要点（HTML 报告：SQL 整批导出 + 交互减法 + `-s`/`-S` 重排）</summary>

- ⚠️ **`-s` / `-S` 语义重排**：`-s` = **强制出报告**（文件名自动取 `<日志名>_报告.html`，
  屏幕只给简要要点）；`-S` = **命令行简要统计**（不出文件、不导 SQL）。
  理由：报告做好后 `-s` 是最高频用法，既然用户已明确要报告，不该再逼他多打一个参数
- ⚠️ **`-s` 不再把几十万条 SQL 刷到 stdout**：不带 `-o` 时完全不往 stdout 写 SQL，
  屏幕上只留统计要点 —— **终于可以接管道**（`| grep` / `| head`）了。
  真要 SQL 就显式 `-o 文件名`；报告路径与统计走 stderr，SQL 才走 stdout
- **每张表新增「导出全部 TopN」按钮**（最慢语句 / 最耗时模板 / 高危操作）：
  点一下把该表所有行的 SQL 下载成 `.sql`（`slow_top10.sql` 等），
  **每条前面一行 `--` 注释头、语句压成单行不折行**，整个文件仍是合法 SQL，可直接跑（见 5.3）
- **去掉重复的 `[展开]` 按钮**：点击摘要文字本就能展开，只留这一个入口；
  同时**去掉逐行 `[存为 .sql]` 按钮**（又占地方又丑，真实需求总是"这一类我都要"）
- 实测回归与 V1.8 逐项一致（3,347,484 / 467,964 / 97.76% / 锁等待 54）；交互自测 26 项全通过
